  - 修法二选一：

## 安全

- **AGENTS.md 开头声明的工具权限在容器里大概率没生效**（2026-10-21 查代码发现，待实测确认）。
  - gh_skill 的 `AGENTS.md` 开头 frontmatter 写了一组 permission：
    - 禁止 edit；
    - skill 只允许 `gaussdb-*`；
    - bash 白名单；
    - 禁止 webfetch / websearch；
    - 禁止访问外部目录。
  - 容器把 AGENTS.md 作为全局规则安装：`docker/Dockerfile:38` 的 `--agents-md /opt/agent/config/opencode/AGENTS.md`。
    opencode 只把它当提示词读，frontmatter 里的权限不会被执行。
  - 容器渲染的 opencode 配置只有 `"permission": {"external_directory": "allow"}`（`docker/podctl.py:78`），没有任何工具限制。
  - 影响：
    - 「只能调用预置技能、不能改文件、不能联网」目前只靠提示词约束；
    - 硬闸门不受影响：网络策略、中间件白名单只读脚本、处置只生成不执行。
  - 实测方法：在 runtime Pod 里让模型写一个文件、执行一条白名单外的 bash、发一次 webfetch，看是否被拦。
  - 修法：把权限写进 `podctl.render_opencode_config` 生成的 opencode.json。
    注意保留 `external_directory: allow`（要读 `/nas/kb`），这一项与 AGENTS.md 里的 `deny` 相反，要以容器为准。
    同时补 `docker/tests/test_podctl.py` 的断言。
  - **实测确认没生效，已修（2026-10-23，待发版）**：权限由 `podctl.opencode_permissions` 渲染进 opencode.json，按镜像里的
    `AGENT_ROLE` 区分（诊断容器不能编辑，导入容器可以 —— kb-init 要写草稿）。`scripts/check-opencode-permissions.py` 用真 opencode
    + 按脚本发工具调用的假模型逐条核对，两种角色各 24 条全部符合预期；已知 opencode 不核对 `export` / `declare -p` 这类声明命令。
    详见 `docs/plans/2026-10-23-credproxy-e2e.md`。提交 `9d34805`。
- **密钥以环境变量注入在智能体主容器里，模型可读到**（2026-10-21 查代码发现，与上一条叠加）。
  - `k8s/templates/runtime.yaml:71-80` 注入到 opencode 主容器的环境变量：
    - 本人中间件令牌 `GRMP_AUTH_TOKEN`
    - 全应用共用的 SM2 签名私钥 `GRMP_SM2_PRIVATE_KEY`
    - 模型服务 `MODEL_API_KEY`
    - 向量库只读口令 `KB_PG_PASSWORD`
    - `OPENCODE_SERVER_PASSWORD`
  - 工具权限没生效，模型执行 `env`、`printenv` 或读 `/proc/*/environ` 就能看到。挡住这件事的只有红线提示词
    （「绝对沉默条款」「输出屏蔽规则」），没有代码兜底。
  - 影响：
    - 中间件令牌按人发放，仍只能调白名单只读脚本，影响限于本人；
    - SM2 私钥全应用共用一把，模型 Key 泄露可被冒用，这两项更敏感。
  - PPT 第 25 页「不读取凭据」、第 26 页「被诱导泄露口令 → 拒答并屏蔽」，在容器版里实际只有提示词这一道。
  - 修法：
    - 短期：配上 opencode 工具权限。bash 只放行技能脚本（`python3 <skills>/gaussdb-*/scripts/*`），
      显式拒绝 `env`、`printenv`、`cat /proc/*`、`set` 等。
      注意 AGENTS.md 那份权限清单里放行了 `cat *`、`grep *`，照搬时要对 `/proc` 与环境变量单独拦。
    - 长期：把中间件令牌与 SM2 私钥移出 opencode 主容器，改由同 Pod 的签名转发副容器持有，
      参照池化沙箱副容器 poolctl 的做法。技能脚本经本地端口请求副容器签名后转发，模型所在进程拿不到密钥。
      模型 Key 是 opencode 自己要用的，可评估改由网关代理注入。
  - **进展（2026-10-23，长期方案已做、待发版）**：凭据代理（`docker/credproxy.py`）。中间件令牌、SM2 私钥、模型 Key 一样都不进
    opencode 的容器：按需模式在同 Pod 的伴生容器 `credproxy`，固定池化在管家（每个槽位两个套接字，中间件与模型分开）。
    技能经 Unix 套接字、opencode 经 127.0.0.1 的模型端口访问，凭据由代理在转发时加上；只往配置的地址、只转两个诊断路径、
    工号按绑定强制写入。测试环境（镜像 `sec-9d34805`、mock 开着完整 SM2 签名）验收全部通过：槽位 / 容器里扫遍全部进程的
    环境与命令行、渲染出的配置，三样秘密都不出现；中间件与模型经代理走通；别的槽位借不到身份；技能级登录 + 健康检查走通。
    `KB_PG_PASSWORD` 已随 v1.3.2 向量库下线一并去掉。详见 `docs/plans/2026-10-23-credproxy-e2e.md`。提交 `9d34805`。
