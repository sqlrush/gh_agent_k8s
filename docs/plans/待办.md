## 客户需求（2026-10-22 沟通）

- **向量库改为 sqlite-vec**（替代 GaussDB DataVec / pgvector）。**2026-10-22 确认：GaussDB 向量库下线**，不再保留该组件。
  - 做法：知识库的向量与词法索引放进一个 SQLite 文件；向量用 sqlite-vec，词法用 SQLite 自带 FTS5，
    存我方分词层切好的词（FTS5 默认不切中文）。索引仍是「文件是真相、可重建」的派生物，换存储不迁数据，重建即可。
  - 已确认：运行镜像的 Python sqlite3 能加载扩展，FTS5 可用（sqlite 3.40.1），不改基础镜像。
  - 要注意：
    - sqlite-vec 未到 1.0，锁定版本；稳定版只有精确检索，我方规模（几万条以内）够用；
    - 知识库在 NAS 上、多个诊断容器同时读：读方只读打开（或启动时拷到本地），只有导入容器一个写方；
    - 去掉 vectordb StatefulSet、`KB_PG_*` 口令与相关网络策略；`kb.yaml` 的 store 配置、部署手册、对接清单同步改。
- **所有技能的慢 SQL 定位都排除内核自己的系统 SQL**（2026-10-22 明确：指 GaussDB 自己产生的系统 SQL）。
  - 现状：只有 sqltune（`systables.py`）、proctune（`sysprocs.py`）会跳过；slowsql、topsql、健康检查的慢 SQL 维度、
    WDR 的 Top SQL 都没排除。
  - 做法：先在 og5 取样，确认「内核系统 SQL」的特征，按两类识别：内核后台线程发起的（WDR 快照、语句历史刷盘、自动清理 / 统计、定时任务等），
    以及只访问系统表 / 系统视图的；
    判定规则收进 `common/` 一处，各技能共用（复用 `systables.py` 的判定）；优先在脚本层过滤，避免改白名单 SQL 让客户重导。
  - 报告里写明「已排除 N 条内核系统 SQL」，不悄悄藏掉。
  - og5 取样（2026-10-22，语句历史近 2 天、`dbe_perf.statement` 按用户）：
    - 内核 WDR 快照线程：应用名 `WDRXdb`、用户 omm，语句形如 `select ?, ?, t.* from dbe_perf.summary_statio_all_indexes t`，每条 75 次；
    - 诊断工具自己发的（含我方智能体，用户 gaussdb）：查语句历史、`generate_wdr_report` 等，只访问系统视图，单条累计最多 17 秒，
      不排除会污染慢 SQL 榜；管理员 gsql 手工查系统视图同理。
    - 规则（命中任一即排除）：① 应用名属于内核后台线程（`WDRXdb` 等，实现时补全名单）；② 语句只访问系统对象
      （`pg_catalog`、`dbe_perf`、`snapshot`、`information_schema`、`pg_*` / `gs_*` 系统表与视图、WDR 系统函数），复用 `systables.py`。
- **固定池化：部署时启动全部 Pod（参数控制，如 16 个），之后不建、不删、不补；16 人以内各自独占，超出的人多个工号共用一个 Pod**。
  - 设计稿：`docs/specs/2026-10-22-fixed-pool-design.html`（图文版，待评审；同名 `.md` 为摘要）。要点：池子改由我方网关管理
    （客户平台只做 SSO）；StatefulSet 固定副本数；每个 Pod K 个槽位容器，一人一个槽位；先给无人在用的 Pod，再给在用人数最少的 Pod；
    **粘性保留**：人走了先写回 NAS，槽位与文件仍归他，回来比对版本号直接用（0–1 秒）；只在缺槽位 / 超保留期时腾挪，
    腾挪时重启容器、清盘，由网关核对容器重启次数。
  - 纠正：v1.2.0 池化把客户原话「回收到 16 个就不回收了」理解成用完即删、不足补建、第 17 人现建，与客户本意不符。
  - **单人资源实测**（2026-10-22，u9500 + 真实 DeepSeek，测试库 og5；容器内读 cgroup，每 2 秒一次）：
    - 空闲（opencode 在跑）实占约 350–500 MiB；一个会话做 WDR 分析峰值 676 MiB（含文件缓存 819），CPU 平均 0.28 核、峰值 0.9 核；
      同一人 3 个会话并发峰值 691 MiB（含缓存 843），CPU 平均 0.48 核、峰值 1.36 核。
    - 结论：每个在用的人约 0.7 GiB 实占 / 0.9 GiB 含缓存、0.3–0.5 核；限制人数的是集群总内存，不是每 Pod 人数。
      每 Pod 人数按「高峰在用人数 ÷ POOL_SIZE」向上取整；集群按「人数 × 0.9 GiB、人数 × 0.5 核，再留 30%」配。
    - 局限：只测了 WDR 一类任务、测试库数据量小；上线前在客户环境装 metrics-server 复测。

## 知识库

- **知识库导入读不了照片：模型能看图，但容器生成的 opencode 配置没声明图片输入**（2026-10-22 用户反馈，截图存于 `opencode_skill/prd/微信图片_20261022182218_528_1215.png`、`…182242_529_1215.png`）。
  - 现象：kb-init 标准化照片时，
    - HEIC 照片：模型说环境里没有 HEIC 解码器，让用户转成 jpg/png 再传；
    - 用户转成 PNG 重传后，read 返回 `this model does not support image input`，一张都没读出来。
  - 原因：
    - kb-init 按设计不做 OCR，照片靠模型用 read 工具看图（SKILL.md「照片 / 截图」一节）；
    - `docker/podctl.py:render_opencode_config` 生成的模型配置只有 `{"name": <MODEL_ID>}`，没有 `modalities`；
    - opencode 1.18.27 的判断是：配置没写 `modalities.input` 含 `image`、自带模型目录里也查不到这个模型时，默认不能看图，read 在客户端就把图片拦下，不发给模型；
    - HEIC 另有一层：镜像里没有解码组件（无 PIL / pillow-heif / heif-convert），read 也打不开 HEIC。
  - 实测确认（2026-10-22）：
    - 直接调 api.deepseek.com 的 `deepseek-flash` 发纯红、纯蓝两张图，都答对 —— 模型本身支持图片输入；
    - 同一个 kb-import 镜像里让 opencode 读一张蓝色 PNG：现在的配置报 `this model does not support image input`，
      只加 `"modalities": {"input": ["text","image"], "output": ["text"]}` 就答出「蓝色」。
  - 修法：
    - `podctl.py` 新增环境变量 `MODEL_INPUT_MODALITIES`（如 `text,image`）写进 `modalities`，默认仍为纯文本
      （部署样例的 qwen3-32b 不能看图，贸然打开会让读图请求报错）；客户现场与本地测试的 agent-config 设成 `text,image`；
      补 `docker/tests/test_podctl.py` 断言；需重建镜像。
    - kb-import 镜像加 pillow + pillow-heif，`kb_init.py scan` 遇 HEIC 自动转 jpg 快照，用户不必自己转。
    - kb-init SKILL.md：read 报 `does not support image input` 时，说明是平台没开图片输入、请找管理员，
      不要让用户转格式（这次用户转了 PNG 白跑一趟）。
  - 修好之前的现场绕法：把照片内容整理成 docx / txt 再导入。

## 安全

- **AGENTS.md 开头声明的工具权限在容器里大概率没生效**（2026-10-21 查代码发现，待实测确认）。
  - gh_skill 的 `AGENTS.md` 开头 frontmatter 写了一组 permission：
    - 禁止 edit；
    - skill 只允许 `gaussdb-*`；
    - bash 白名单；
    - 禁止 webfetch / websearch；
    - 禁止访问外部目录。
  - 容器把 AGENTS.md 作为全局规则安装：`docker/Dockerfile:38` 的 `--agents-md /opt/agent/config/opencode/AGENTS.md`。
    opencode 只把它当提示词读，frontmatter 里的权限不会被执行。
  - 容器渲染的 opencode 配置只有 `"permission": {"external_directory": "allow"}`（`docker/podctl.py:78`），没有任何工具限制。
  - 影响：
    - 「只能调用预置技能、不能改文件、不能联网」目前只靠提示词约束；
    - 硬闸门不受影响：网络策略、中间件白名单只读脚本、处置只生成不执行。
  - 实测方法：在 runtime Pod 里让模型写一个文件、执行一条白名单外的 bash、发一次 webfetch，看是否被拦。
  - 修法：把权限写进 `podctl.render_opencode_config` 生成的 opencode.json。
    注意保留 `external_directory: allow`（要读 `/nas/kb`），这一项与 AGENTS.md 里的 `deny` 相反，要以容器为准。
    同时补 `docker/tests/test_podctl.py` 的断言。
- **密钥以环境变量注入在智能体主容器里，模型可读到**（2026-10-21 查代码发现，与上一条叠加）。
  - `k8s/templates/runtime.yaml:71-80` 注入到 opencode 主容器的环境变量：
    - 本人中间件令牌 `GRMP_AUTH_TOKEN`
    - 全应用共用的 SM2 签名私钥 `GRMP_SM2_PRIVATE_KEY`
    - 模型服务 `MODEL_API_KEY`
    - 向量库只读口令 `KB_PG_PASSWORD`
    - `OPENCODE_SERVER_PASSWORD`
  - 工具权限没生效，模型执行 `env`、`printenv` 或读 `/proc/*/environ` 就能看到。挡住这件事的只有红线提示词
    （「绝对沉默条款」「输出屏蔽规则」），没有代码兜底。
  - 影响：
    - 中间件令牌按人发放，仍只能调白名单只读脚本，影响限于本人；
    - SM2 私钥全应用共用一把，模型 Key 泄露可被冒用，这两项更敏感。
  - PPT 第 25 页「不读取凭据」、第 26 页「被诱导泄露口令 → 拒答并屏蔽」，在容器版里实际只有提示词这一道。
  - 修法：
    - 短期：配上 opencode 工具权限。bash 只放行技能脚本（`python3 <skills>/gaussdb-*/scripts/*`），
      显式拒绝 `env`、`printenv`、`cat /proc/*`、`set` 等。
      注意 AGENTS.md 那份权限清单里放行了 `cat *`、`grep *`，照搬时要对 `/proc` 与环境变量单独拦。
    - 长期：把中间件令牌与 SM2 私钥移出 opencode 主容器，改由同 Pod 的签名转发副容器持有，
      参照池化沙箱副容器 poolctl 的做法。技能脚本经本地端口请求副容器签名后转发，模型所在进程拿不到密钥。
      模型 Key 是 opencode 自己要用的，可评估改由网关代理注入。
