## 技能（faultlab 第二轮，2026-10-24 全量重跑后仍未报出或新发现的）

第一轮测出的 12 个问题已在 v1.4.0 修好（见版本说明）。第二轮用修好的技能在 og5 上全量重跑一轮
（快照 3184–3191），逐项结果在 gh_skill `tools/faultlab/expected.yaml` 的 actual（以「2026-10-24 第二轮」开头）。

- **lockwait**
  - 「互斥关系」只解释前 5 对（`lockwait.py` 的 `pairs[:5]`）：一条长链占满名额，其余链的锁类型说明不显示。
  - 瞬时模式下 VACUUM FULL 那几对写「阻塞链数据缺失，未能确认根 holder」，不给根也不给处置；时段回看能找到根。
  - 没解释 DDL 排队放大（读被排在 ALTER 后面），没点明外键引起的等待。
  - 时段回看在落表范围内一个样本都没有时按「回看不了」处理（分不清是当时没活动还是重启丢了未落表的样本），待在真实环境确认口径。
  - 精确的等锁秒数要另加 statement_history 或 gs_asp 的脚本（当前的语句统计里没有锁等待列），这次没做。
- **vacuum**
  - 自己的取数没设等锁超时：VACUUM FULL 期间查那张表被挡、语句超时 rc=2。
  - 不识别表级限速（`autovacuum_vacuum_cost_delay` / `cost_limit`）；两阶段事务没给 `ROLLBACK PREPARED`，复制槽没给删槽或让消费端跟上的具体做法。
- **health**：SLOWSQL_TOP / ACTIVE_SQL_HOT 覆盖不到高频中等慢的 SQL（平均 131 ms、调用上万次），要靠 topsql。
- **waitevent**：多种故障混在一起时轻量锁被锁等待稀释，出不了 WAIT_LWLOCK_HEAVY；落盘读（BufFileRead 70 秒）只占 DATA_IO_TIME 的一小部分，出不了 DBTIME_IO_HEAVY。
- **lockwait deadlock-log**：日志里只有两条 UPDATE 时认不出「锁升级」形态（看不到前面的 SELECT），从日志无法区分，属限制。
- **memanalyze**
  - 要报出 SQL 落盘需要白名单多取 `max_spill_size`；og5 上这一列看起来按会话累加、单位不确定，等在真实环境核实口径再加。
  - openGauss-lite 上 WLM 作业视图（L4 / L5）参数都开着也一直是 0 行，是内核限制。
- **sqltune**
  - 根因规则只认 openGauss / PG 的 TEXT 计划，GaussDB 的表格格式计划认不出（只是不报，不误报）。
  - explain、proctune 里还各有一份旧的 scan_plan 规则，没接上新的根因规则。
  - 常量 `LIKE 'abc%'` 在非 C 排序规则下用不上普通索引这一条没做（证据包里没有 lc_collate）。
  - 其余原样保留的小问题：schema 推测成连接用户名（不影响结论）；`explain --sql-id` 拒绝归一化文本。

## 测试工具（faultlab）

- V4 的逻辑复制槽会让 WAL 持续堆积（全量一轮约 10 GB），跑完 cleanup 删槽后要等 checkpoint 回收；og5 平时就留着很多 WAL，WAL 守卫看的是增量，没触发。
- V5 在全量混跑里 autovacuum 一轮也跑不完：3 个 worker 被清不掉的表占满（实例级 `autovacuum_max_workers=3`，faultlab 不改实例参数）。
- S5（统计缺失导致估算偏差）到 2026-10-24 复验才真正造出来（估 733、实际 11026）：sqltune 会不会建议 ANALYZE、memanalyze 能不能报出估算偏差，要等下一次全量跑检验。
- L5 造不出来：这个内核判断子事务可见性不经过 SubtransControlLock / CLogControlLock，已照实写进 expected.yaml。
