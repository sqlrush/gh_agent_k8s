看稿之前，三件事要你拍板

① 大盘的数字从哪来 —— 这是整个前端镜像最大的架构问题 dsh-k8s 的大盘读的是持续采集器写进 PG 的存档。我们没有采集器：技能在用户 Pod 里按需跑一次、把 JSON 打到标准输出，然后什么都不留。所以四个大盘要有数据，必须先回答「报告存在哪、前端怎么读到」。
  • A. 技能落盘到本人 NAS 目录 + 用户 Pod 里多开一个只读端口：health / topsql / wdr / kb 跑完各写一份 JSON 到 /nas/me/reports/<技能>/<时间>.json；podctl 起一个极小的静态 HTTP（4097）只读这个目录；网关把 /reports/* 也代理到用户 Pod。代价：多一个监听端口、NetworkPolicy 多一行、podctl 多一个子命令；好处：历史天然有（就是文件），隔离天然有（网关按工号代理，前端拿不到别人的）。
  • B. 前端 Pod 直接只读挂 NAS，按工号读目录：少一个端口。代价：前端 Pod 能看到所有人的目录，隔离只剩「前端代码按网关传来的工号过滤」这一层软的——违反接入手册里「隔离靠不挂载而不是靠权限」那条。
  • C. 从 opencode 会话里解析工具输出：不改技能。代价：要在会话消息里找 JSON，格式脆；只有本会话跑过才有；历史要扫全部会话。
A。多一个端口换来的是隔离不打折、历史不用另做。C 我实测过 GET /session/{id}/message 能拿到 parts，但把大盘建在解析对话上，改一次提示词就可能全塌。
② 「深挖 →」跳到哪 —— 去掉 deepseek-harness 的对话页之后，对话在哪发生 你要求去掉对话页面。四个大盘的每个「深挖 →」「调优 →」都需要一个能对话的地方。现在用户对话走的是 opencode 自带的 Web 界面（网关代理到用户 Pod）。
前端镜像只做大盘；「深挖」= 调 opencode API 建一个会话并发第一句（带上这条发现的上下文），然后跳转到 opencode Web 的那个会话 URL。两个界面并存，侧栏「对话」分组就是跳过去的链接。不在前端镜像里再做一套对话 UI。
③ 两个功能取舍，各自要改技能侧
  • Top SQL 多维度占比：dsh-k8s 有 DB Time / CPU / IO 三根堆叠条，我们的 topsql 只取六列。要的话白名单要加列，客户侧走版本 DML——现在设计稿只画了「当前维度」一根条。
  • 知识库「最近检索」表：要 kb query 落检索日志（本人目录一行一条）。不要的话这张表去掉。
Top SQL 先按六列做，多维度等客户白名单能加列再说；「最近检索」要——它是「缺口清单」的来源，没有它缺口清单就只能从 findings 反推。

不用拍板、我会直接这样做的

  • 去 logo：上游有 sidebar.brand.mark / sidebar.brand.name 两个插槽，ui-brand-official 插件就是往里注册海豚 logo 的——我们不装它、装自己的一个。不用 CSS 硬盖。
  • 去对话页：ui-conversation / ui-chat 是独立客户端插件，profile 里不装即可；主区用 route / mainView 插槽装四个大盘。
  • 四个大盘 = 一个客户端插件包 ui-gaussdb-dashboards（四个页面共用取数层与 chart 组件），不拆四个包——dsh-k8s 拆得太碎，CLAUDE.md 里自己记了「新建插件包三处缺一不可」的坑。
  • 图表沿用 dsh-k8s 的 chart-kit 思路（Bars / Gauge / Line / Pie / StackedBar / RankList / Sparkline），自绘 SVG，不引第三方图表库。
  • 零按钮：只有文字链。数字全部来自技能脚本的确定性判定，模型不改级别。
  • 前端镜像无状态、不挂 NAS（按方案 A）、不带技能，一个共享 Deployment，经网关拿工号。

看稿的顺序建议

  • 先看健康检查（信息最密，其它三页的语言都从它来）→ WDR（与它最像）→ Top SQL → 知识库。
  • 每页的黄色说明里写了「与 dsh-k8s 的差别」——那些差别都是因为数据来源不同，不是偷懒；你要是觉得某个差别不能接受，就是在说「要加采集器」，那是另一个镜像的事。
