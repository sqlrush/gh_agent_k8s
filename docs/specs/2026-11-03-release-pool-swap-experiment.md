# 发版台:池子在线替换实验(2026-11-03)

发版台要在池子对外服务的同时把新版本换上去(设计决定见 `docs/prototypes/release-r1/README.md` 第 3 条)。
动手写之前在 OrbStack 测试环境(agent-v1.4.3,3 Pod × 3 槽位 + 管家,StatefulSet OnDelete)上做了 7 个实验,
只用测试工号 u9500 与空闲槽位。「新版本」用同一个运行时镜像打的新标签(镜像内容不变,只让容器定义变化),
实验 7 用只替换了 `poolslot.py` 的叠加镜像。实验完全部换回原镜像,测试环境复原。

## 结论

1. **单个槽位可以原地换镜像**:`kubectl patch pod` 只改这个槽位容器的 `image`,kubelet 报
   `Container slot-N definition changed, will be restarted`,只重启这一个容器,同 Pod 其他槽位与管家不动。
2. **推荐顺序是「腾挪 → 紧接着换镜像 → 核验」**,不是「直接换镜像」:
   - 在用的先等不忙,再转保留(写回 NAS);
   - `/admin/pool/evict` 让槽位进入清理中(不再接受绑定与恢复),紧接着 patch 镜像;
     腾挪发的 `exit` 与镜像变化引起的重启合并成**一次**重启;
   - 新容器运行后 `/admin/pool/verify`,核验通过记下新容器的真实 ID → 空闲(新版本)。每个槽位约 3 秒。
   - 这条路用 agent-v1.4.3 现有代码就能走,第一次升级不依赖任何修复。
3. **直接换镜像会撞上一个原有缺陷**(已修,见下):安静的槽位重启后管家沿用旧容器 ID,下一个人转保留后恢复被拒。
4. **会话完整接上**:转保留写回 NAS 后换镜像,同一会话的下一句在新容器上载入、模型答出换镜像之前告诉它的暗号。
5. **换管家会把本 Pod 在用的槽位全部转保留**(管家收到 SIGTERM 时的保护逻辑):空闲时换,用户下一句自动恢复(约 3 秒);
   请求进行中换,那次回答被中断(`MessageAbortedError`,只写出一半)。→ 只在本 Pod 所有槽位都不忙时换管家。
6. **「会话忙」的判断**:槽位每 5 秒查一次 opencode `/session/status`(busy / retry 即忙),管家每 2 秒读回执。
   实测请求开始后约 5 秒才变忙、结束后约 4 秒才变闲;不到 5 秒的请求可能一次都不被标为忙。
   → 转保留前要求 `busy=False` 且距上次忙 ≥ 10 秒;转保留应答里的 `aborted_running` 是事后的权威信号,如为真要记下来。
7. **镜像判断不能看 `containerStatuses[].image`**:两个标签指向同一镜像时,它显示运行时先认识的那个名字(实验里一直显示旧标签)。
   判断「换好了」看 spec 的 `image`、containerID 变化与 `imageID` 摘要。
8. StatefulSet 的 `currentRevision` / `updateRevision` 在测试环境本来就不一致(OnDelete 下不会自动跟进),
   不能拿来判断 Pod 是否新模板;原地换镜像后 Pod 的 revision 标签也还是旧的。发版台以每个容器的 spec / imageID 为准,
   同时 `kubectl apply` 新的 pool.yaml,保证以后重建出来的 Pod 也是新版本。

## 实验记录

| # | 做什么 | 结果 |
|---|---|---|
| 1 | 空闲槽位直接 patch 镜像 | 约 2 秒:新容器、新 boot、盘已清空,管家「重启后已清盘,空闲」,不经网关核验 |
| 2 | u9500 在用 → 转保留 → 直接 patch 镜像 → 同一会话继续 | 转保留干净写回 0.1 秒(会话库 106.9 MB);约 5 秒回到空闲;下一句绑到新容器、答出暗号,共 2.9 秒 |
| 3a | 长请求(11 秒)期间每秒看回执 | busy 开始后 5 秒变真、结束后 4 秒变假 |
| 3b | 长请求进行中转保留 | 模型已在转保留前答完(`aborted_running: false`);回答完整 |
| 3c | 实验 2 之后再让 u9500 恢复 | **一直 503「正在为您准备环境」**:管家回 `restarted`(容器 ID 对不上),网关当成稍后重试 —— 即结论 3 的缺陷 |
| 4 | 推荐顺序:腾挪 → patch → 核验(两个槽位,顺便换回原镜像) | 每个约 3 秒,只重启一次,核验记下新 ID;卡住的 u9500 随之解除 |
| 5 | 推荐顺序端到端 + 之后再转保留 / 恢复 | 等不忙 9 秒 + 替换约 5 秒;新容器上答出暗号;再转保留后恢复正常(resume,2.7 秒) |
| 6a | 槽位在用但空闲时换管家 | 管家 2 秒起来,该槽位被转保留;下一句自动恢复,3.6 秒 |
| 6b | 长请求进行中换管家 | 回答被中断(`MessageAbortedError`,写出 765 字) |
| 7 | 修复后的管家(叠加镜像)重放实验 2/3c | 安静重启 → 绑定 → 转保留 → **恢复成功** |

实验 7 期间测试机负载很高(与本实验无关的其他任务),k8s API 出现过一次 TLS 握手超时,那一步慢了 9 分钟;结果不受影响
(转保留时 u9500 确实在用,恢复确实走了 resume)。

## 原有缺陷:安静重启后沿用旧容器 ID

`poolslot._on_new_boot` 的安静路径(空闲,或已确认停下的保留)把重启前的 `container_id` 带进了新记录;`begin_bind`
优先用管家记的那个(本意是「核验过的比网关视图可靠」),于是租期里记的是旧 ID;转保留后恢复时网关带来真实的新 ID,
对不上 → 409 `restarted`。网关把它列在重试原因里、不记日志,清扫也不会腾挪这个保留槽位(没脏、没过期、本人不在别处),
用户一直看到「正在为您准备环境」,直到保留天数到期。

**生产同样会发生**:空闲槽位因崩溃、OOM、探针失败重启过一次,之后第一个在这里被转保留的人就会卡住。
修法:安静路径不沿用旧 ID(留空),绑定时记网关现读的那个。分支 `fix/pool-quiet-restart-cid`,带复现单测,
docker / gateway / scripts 测试全绿;应随 agent-v1.4.4 发出。

## 发版台的池子替换算法(据此实现)

前提:release.yaml 声明新版本可与旧版本混跑;否则按 Pod 整体替换(等本 Pod 都不忙 → 删 Pod → StatefulSet 按新模板重建)。

```
kubectl apply 新 pool.yaml(OnDelete:现有 Pod 不动,只保证以后重建的是新版本)
对每个 Pod:
  对每个槽位(spec 镜像已是新的就跳过):
    在用:等 busy=False 且距上次忙 ≥ 10 秒(超过上限交给运维:继续等 / 强制转保留)→ retain(记下 aborted_running)
    保留但写回不干净:等管家重试写回(evict 会被拒 not_synced),超过上限交给运维
    evict → 立即 patch 该槽位镜像 → 等新容器运行(containerID 变、spec 与 imageID 对上)→ verify → 空闲
  管家:等本 Pod 所有槽位都不忙 → patch 管家镜像 → 等 Pod 重新可达(在用的人被转保留,下一句自动恢复)
```

## 需要的代码改动

- 网关 `/admin/pool` 摘要加上每个槽位的 `busy`、`busy_at`(管家 `/pool/status` 已有,摘要没透出)。
- (可选,降低竞态)管家增加「维护中」:不接受绑定与恢复,重启清盘后自动回到空闲 —— 让「判定不忙」到「转保留」之间
  新来的请求排队几秒,而不是被中断。第一版先不做,靠等待窗口 + 记录 `aborted_running`。
- 上面的容器 ID 缺陷修复。
