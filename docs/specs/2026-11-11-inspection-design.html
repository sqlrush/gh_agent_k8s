0. 结论

推荐做法：采集走确定性脚本、模型只做汇总与深挖。新增一个「巡检服务」（编排 + 执行，跑在集群里，复用运行时镜像里的技能脚本）， 按清单逐实例、逐库调用现有技能脚本的 --format json 输出，结果按现有报告契约（common/reports.archive：latest / index / targets）落到 NAS 的共享巡检目录； 汇总器在同一应用内做跨库排名；模型每个应用只调用一次，用来写巡检摘要；发现问题后「深挖 →」再开智能体会话，这一步复用现有的网关和池化槽位。
不推荐「每个库开一次智能体会话让模型去巡检」。按 11-09 实测（agent-v1.4.10，每题平均送入模型 25.4 万 token、49 秒、21.5 次中间件调用）， 一个 30 个库的应用每天巡检一次，就要约 760 万 token、占用池化槽位半小时以上，而且每次输出不一样，没法排名、比较。 确定性采集一次只要 1～2 分钟，模型摘要约 3 万 token，级别由脚本按阈值判定（模型不改级别，这是现有大盘的规矩），结果可以比较、可以排名、可以复跑。
4 种触发源：人对话（现有）、定时任务、外部调用、监控告警
3 档巡检套餐：快检（告警）、日检、深检（周）
~1.5 分钟一个应用（10 实例 / 30 库）的日检耗时，4 路并行
~3 万 token每个应用每次巡检的模型开销（仅摘要）
5 条为了按库归属需新增的只读白名单脚本
约 7～8 周P0 + P1 + P2 合计（P0 约 3 周可上线日检与大盘）

1. 现状与目标

1.1 现状（agent-v1.4.11）

方面现在怎么做对巡检意味着什么
谁触发只有人：SSO 认人 → 网关按工号把对话转到本人的池化槽位（opencode）→ 模型按技能说明调用脚本。巡检要一个非人的身份和一条不经过浏览器的触发路径。
采集技能脚本只读、只跑白名单，经 GRMP 中间件调用；health / topsql / wdr / vacuum / lockwait / waitevent / config 都有 --format json，Finding 统一在 common/finding.py（severity 0～3 由脚本按阈值定，模型不得更改）。采集与判定已经是确定性的，可以直接批量跑，不需要模型参与。
结果common/reports.archive 把 JSON 存到本人 NAS 目录：<skill>/<实例键>/latest.json · index.json、<skill>/targets.json，每个实例保留 50 份；说明类字段去掉地址。巡检结果沿用同一契约，现有单库大盘不用改格式就能读。
大盘纯静态前端（/dash/*），浏览器经网关取 /reports/*（转到本人 Pod 的 4097 只读端口）；健康 / Top SQL / WDR / 知识库四个大盘，一次只看一个实例（库）。巡检大盘是共享数据（应用级、不属于某个人），要新的数据口和权限。
库v1.4.11 起，登录时给了业务库就带 dbName，对象类脚本（表、索引、统计信息、死元组、存储过程）在业务库上执行；SQL 历史、WDR、会话、锁仍是实例级。一个实例上有多个业务库时，对象类要逐库跑，实例级只跑一次。

1.2 目标

  • 触发多样化：定时任务（每日 / 每周）、外部系统调用（任务系统、运维平台按需发起）、监控系统告警回调（发现生产问题后自动复核），与人对话并存。
  • 应用 / IDC 视角：一个应用（或一个 IDC）下所有实例与库一屏看全；各类排名在同一应用的所有库之间统一排；能下钻到现有单库大盘、能一键深挖。
  • 可比、可追溯：同一口径、同一阈值，每次巡检可与上次比；每条结论能追到脚本、SQL、时间窗口和触发源。

1.3 不做的事（本方案范围外）

  • 不做持续采集器、分钟级曲线（与现有大盘的约定一致：没有采集器就没有曲线；趋势按「巡检次数」画）。
  • 不做自动处置：巡检只读，只给结论和建议，红线不变（不改参数、不建 WDR 快照、不执行业务 SQL）。
  • 不替代监控系统：监控负责「发现」，巡检负责「复核 + 归因 + 建议」。

4.1 一次巡检怎么跑

① 触发定时 / API / 告警，生成 run（带触发源、套餐、范围）
→
② 展开按清单展开成任务：每实例 1 个「实例级」任务 + 每库 1 个「库级」任务
→
③ 执行同一实例串行、不同实例并行（默认 4 路）；登录（--ip / --database）→ 跑脚本 → 存档
→
④ 汇总按应用排名、与上次比较、写 summary
→
⑤ 摘要模型写一段应用级结论（可关）
→
⑥ 通知订阅人 / 回调；告警触发的回写监控

4.2 身份、权限与审计

  • 巡检服务账号（默认 insp-bot，可配置）：沿用「按人下发 GRMP 令牌」的机制，令牌放在 grmp-token-insp-bot（Secret，只挂给巡检服务）。需要行方为服务账号单独授权（见第 14 节）。
  • 审计：每次中间件调用记录执行人 = 服务账号，外加触发源（task / api / alert）与触发编号（run_id、调用方、告警编号），沿用 common/audit.py 的执行人字段（GSDB_USER_ID）。
  • 外部调用鉴权：调用方系统各发一个 API 令牌 + 来源网段白名单（与网关的信任凭据同一思路：至少一道、常数时间比较、没配就拒绝启动）。
  • 看大盘的权限：沿用 SSO 角色头。默认角色 inspect-viewer 能看全部；可按应用授权（inspect:<应用编号>）。发起巡检要 inspect-operator。

4.3 并发、限流、超时与重试

项默认值理由
全局并行4 路中间件并发能力未知（第 14 节问题 4），先保守；可配置
同一实例串行（1 路）实例级与该实例下各库的对象类任务排队执行，避免同时给一个实例压多条查询
中间件调用速率≤ 5 次 / 秒（全局）令牌桶；告警快检有单独的小额度，不被日检挤掉
单条脚本超时沿用脚本 --timeout（默认值不变）与对话里一致
单库任务上限5 分钟超时记「采集超时」，不阻塞别的库
重试网络 / 中间件 5xx 重试 2 次（退避 10 s、30 s）；SQL 报错、权限不足不重试权限类错误重试没有意义，直接记原因（用登录与自检已有的错误说明）
巡检窗口日检默认 02:00–05:00，可按应用改避开业务高峰；告警快检不受窗口限制
压力保护实例活跃会话 > 阈值时跳过库级对象检查，只做实例级出了问题的实例上不雪上加霜；记「因实例繁忙跳过」

4.5 成本估算

做法一个应用（10 实例、30 库）日检一次可比性
每库开一次智能体会话模型输入约 760 万 token（按实测每题 25.4 万）、输出约 15 万；串行约 30 分钟，或占 30 个槽位每次措辞与取数路径不同，难以排名

7. 跨库统一排名口径

原则：① 只把能归属到库的指标放进「库榜」，实例级指标单独成「实例榜」，库榜上用「所在实例」标签带出实例的状态，不把实例级数据拆到库上； ② 不编综合分（现有健康大盘的规矩：报告抬头用确定性状态带，不编造单一分数），默认排序按级别带；③ 比率类指标要有最小样本量，量太小不参与排名、标「样本不足」；④ 每个数字都能点开看来源脚本与时间窗口。

Top SQL（总耗时、CPU、IO、写入行数）dbe_perf.statement（topsql.top_sql）这张视图没有库名列；按库看 SQL 用「慢 SQL」维度（执行历史有 db_name，但只含被记录下来的语句，覆盖率在页面上标明）

连接使用率、线程池health 连接维度上限是实例级参数

7.3 归一化与对比

  • 按窗口折算：增量类指标统一折成「每秒」或「每小时」，不同实例的快照间隔不同也能比。
  • 同应用分位：每个值旁标出在本应用内的分位（P50 / P90），一眼看出是不是离群。
  • 自身基线（P2）：与该库最近 7 次巡检的中位数比，给「偏离倍数」，可按偏离倍数排名——解决「大库天然排在前面」的问题。
  • 规格差异：清单带了实例规格时，在实例榜显示规格列；比率类指标不受规格影响，优先展示。
  • 与上次比：问题按 code + 对象 匹配，标「新增 / 持续 / 已消除」。

13. 风险

风险应对
巡检本身给生产加负载只读、白名单、同实例串行、令牌桶、巡检窗口、繁忙跳过库级；上线前在测试环境量出每实例调用次数与耗时
中间件并发 / 限流未知默认 4 路、5 次 / 秒，可配；接口返回限流时退避并在大盘标明
dbName 切库在行方未生效库级维度记「未采到」并写原因，实例级照常；大盘覆盖率如实显示
排名口径有争议（大库天然靠前、实例级数据被误读成库的）库榜 / 实例榜分开；比率与分位优先；P2 加自身基线；每个数可追到脚本与窗口
服务账号权限过大只授白名单只读执行；令牌只挂巡检服务；审计带触发源
告警风暴去重、合并、额度与排队
模型摘要说错只读汇总结果、不调工具；引用编号与级别校验，不过就不显示
A / M 兼容模式库库级对象脚本先在行方环境验证；未验证前该类库库级维度标「未验证」
