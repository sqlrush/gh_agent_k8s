# 设计：Fuyao 沙箱运行模式（`RUNTIME_MODE=fuyao`）

日期：2026-11-17。基线：`agent-v1.4.14`。分支：`feat/fuyao`。目标版本：`agent-v1.5.0`。

## 1. 目标与范围

在 openFuyao 沙箱平台（OpenSandbox + Flux + E2B / Firecracker 微型虚拟机）上运行智能体：**每个用户一台沙箱**，知识库管理员的导入环境同样一台沙箱。

- 网关新增第三种运行模式 `fuyao`，与 `ondemand`（按需建 Pod）、`pool`（固定池化）并列，改配置切换；现有两种模式的代码路径不动。
- 留在 K8s 的组件：网关、大盘前端、标准知识库安装 Job，以及本设计新增的两个集群服务——凭据代理服务、状态服务。
- 不在范围：平台自身的安全加固（见 §9 平台前提）。

## 2. 平台实测事实（决定设计的约束）

以下均为 PoC 实测或读平台源码所得，平台升级后需重新核对。

| 事实 | 对设计的影响 |
|---|---|
| 创建沙箱：`POST /v1/sandboxes`，`extensions.sandboxGroup` 指定沙箱组；不带 `extensions.poolRef` 时必须带 `resourceLimits`；`image.uri` 填模板名 | 网关后端按此组装请求 |
| 建沙箱 0.1–0.6 秒 | 首次进入的等待主要在启动器与状态载入 |
| 虚拟机规格（vCPU、内存、磁盘）由**模板**决定，沙箱组规格只是 K8s 侧预留 | 构建模板时定足规格 |
| 创建请求里的 `env`、`entrypoint` 不进虚拟机 | 启动器：沙箱建好后经 envd 下发配置并启动 |
| 创建请求里的 `volumes` 不往下传，Flux 的 Sandbox 对象没有卷字段 | 沙箱只有本地盘；NAS 由集群侧**状态服务**读写 |
| 出网规则不往下传（只传模式字段） | 出网限制由平台在宿主机侧实现（§9） |
| envd（49983）的 Connect 接口可按命令带环境变量、指定用户执行；它会等待子进程 | 启动器以 `systemd-run` 起后台服务 |
| 虚拟机在 Pod 网段有独立地址，集群内可直连任意端口，SSE 实时 | 网关直连 `虚拟机地址:4096 / 4097 / 4095`，转发代码沿用 |
| 虚拟机 DNS 为公网地址，解析不了集群域名 | 集群服务一律用 ClusterIP 下发 |
| `PATCH /v1/sandboxes/{id}/metadata` 可用，metadata 即 Sandbox 对象标签，可按 metadata 列举 | 工号、角色、活动时间记在 metadata |
| 暂停约 2 秒、恢复约 3 秒，内存快照完整续上 | 粘性保留：闲置时暂停、回来恢复 |
| **暂停的沙箱不占承载 Pod 的名额**：每个承载 Pod 2 台、只有 1 个承载 Pod 时，暂停一台后新沙箱马上建在同一个承载 Pod 上（该 Pod 上 2 台运行 + 1 台暂停）；满员前建不出来，调度器报 `503 no available agent`（2026-11-18 实测） | 容量 = 承载 Pod 数 × 每 Pod 台数，只算**同时运行**的沙箱；容量按同时在用的人数规划，闲置暂停的人不挤占新来的人 |
| **平台不会按需自动扩到 `agentPodMax`**：`agentPodMax` 从 1 调到 3 没有新起承载 Pod，`agentPodMin` 调到 2 才多起一个（2026-11-18 实测） | 承载 Pod 数跟着 `agentPodMin` 走，要多少就把最小值设成多少；大盘不写「可扩到最大值」 |
| 沙箱组满员时，OpenSandbox 把调度器的 `503 no available agent` 包成 `500`（日志 `flux create_sandbox failed`，平台缺陷） | 网关把建沙箱的 5xx 都按「平台暂时没有空位」处理：等待页、自动重试，平台原话记日志（`PoolWait platform_busy`）；4xx 仍是错误 |
| 恢复后虚拟机地址会变，而 `/endpoints/{port}` 仍返回旧地址 | 见 §6.3 地址发现 |
| 删除即时生效，虚拟机内收不到退出信号 | 销毁前由网关触发收尾同步 |
| 建沙箱带 `timeout` 时平台到点直接删（不发信号），续期接口回 409（不支持），`timeout` 上限 86400 秒；**不带 `timeout` 就没有到期时间**（端到端实测） | 默认不带 `timeout`，生命周期全由网关管；平台强制要求时，网关在到期前 15 分钟收尾后删除（§6.2） |
| 单台查询 `GET /v1/sandboxes/{id}` 不带业务 metadata、`createdAt` 不准；列举与单台查询都不回 `expiresAt`，只有建沙箱的回包带（端到端实测） | 一律从列举里取沙箱与 metadata；到期时刻建沙箱时自己记进 metadata（`gsdb-expires`） |
| 模板构建：`POST /v3/templates`（名称、vCPU、内存）+ `POST /v2/templates/{tid}/builds/{bid}`（`fromImage`），带占位层的 runtime 约 70 秒建好 | — |
| 构建服务的容器里没有根证书，拉不了公网仓库；它拉取时对本机地址走 HTTP、不校验证书，且跑在主机网络上 | 构建时在构建服务所在主机上起只读临时仓库（`scripts/oci-serve.py`，只听 127.0.0.1），不需要任何仓库账号 |
| 模板磁盘 = 镜像大小 + 平台固定余量（约 0.5GB），模板参数里的 `diskSizeMB` 不生效；vCPU、内存按模板参数生效 | 模板层里放一个全零的占位文件撑大磁盘（6GB 占位 → 磁盘 9.3GB），启动器首次启动时删除，空出约 8GB 给用户状态；全零数据压缩后只有几 MB，宿主机上每份模板约 0.8GB |
| 构建会给镜像装上 systemd、SSH、时间同步，并建一个带 sudo 的默认用户 `user` | 我方服务一律以镜像里无 sudo 的 `agent`（uid 1000）运行 |

## 3. 组件与通路

| 组件 | 位置 | 职责 |
|---|---|---|
| 网关 | K8s | 认身份；为每人申请诊断 / 导入沙箱；签发沙箱令牌；下发配置并启动；转发；闲置暂停与回收 |
| 凭据代理服务 | K8s（runtime 镜像） | 持有模型 Key、SM2 私钥、各工号 GRMP 令牌；按沙箱令牌认人，加凭据后转发 |
| 状态服务 | K8s（runtime 镜像，挂 NAS PVC） | 用户状态载入、增量回写、收尾、按人加锁；知识库发布与按版本拉取；报告只读 |
| 诊断沙箱 | 虚拟机（runtime 模板） | opencode + 诊断技能；启动器；状态同步客户端；本地盘 |
| 导入沙箱 | 虚拟机（kb-import 模板） | opencode + 知识库技能；剪藏接收；知识库工作副本，完成后发布 |

通路：
1. 浏览器 → SSO → 网关；
2. 网关 → OpenSandbox：建、删、暂停、恢复；
3. 网关 → 沙箱 envd：下发配置、启动、收尾；
4. 网关 → 沙箱 4096 / 4097 / 4095：对话、报告、剪藏；
5. 沙箱 → 凭据代理服务：模型与 GRMP；
6. 沙箱 ⇄ 状态服务：状态与知识库；
7. 状态服务 ⇄ NAS；
8. 网关 → 状态服务：报告只读。

## 4. 身份与令牌

- 网关为每台沙箱生成三样东西：对话口令（同现在，按人沿用，存在 Secret `pod-auth-<工号>`）、报告令牌（按沙箱 ID 派生）、**沙箱令牌**（新增）。
- **沙箱令牌自带签名**（`gateway/sbxtoken.py`）：内容是沙箱 ID、工号、环境种类和签发时间，用控制密钥（Secret `sandbox-control`，与固定池化同一把）派生的子密钥做 HMAC 签名。
- 凭据代理服务、状态服务持有同一把控制密钥，**各自校验，不需要网关逐个登记**，也不需要它们之间同步状态。按令牌里的工号限定：凭据代理写入的工号、状态服务允许访问的目录，都只能是本人的；知识库发布只认种类为导入环境的令牌。
- 令牌只存在于它那台沙箱里：沙箱删除即随之消失，暂停后恢复继续有效。不能单独吊销某一张，这是相对登记表的取舍——换来的是多副本、重启、扩缩都不需要额外的一致性机制。
- 口令、报告令牌、沙箱令牌都只经 envd 下发给本沙箱，不写日志。

## 5. 启动器（沙箱内）

`podctl fuyao-start`，由网关经 envd 以 root 调用，参数和配置以环境变量形式传入：
1. 写配置到 `/run/gsdb/env`（0600）；
2. 凭沙箱令牌向状态服务**载入**本人状态到本地盘（首次为空）；诊断沙箱另拉取客户知识库只读副本；
3. 以 `systemd-run` 用普通用户起 `entrypoint.sh`；它读 `/run/gsdb/env`，同步回写改走状态服务；
4. 等 4096 就绪后返回。

`podctl fuyao-stop`：完整同步一次，等状态服务确认后返回。网关在暂停（可选）和删除前调用。

## 6. 网关

### 6.1 接入

Fuyao 路由器实现与固定池化路由器相同的接口（`target()` / `note_activity()` / `forget()`；异常 `NotActive` / `PoolFull` / `PoolWait`），`server.py` 的池化转发路径直接复用。诊断与导入是两种 kind，对应两套模板与沙箱组。

### 6.2 生命周期

| 事件 | 动作 |
|---|---|
| 交互请求，本人无沙箱 | 建沙箱（metadata：工号、kind、模板）→ `fuyao-start`（下发配置与签名的沙箱令牌）→ 探活 → 返回目标 |
| 交互请求，本人沙箱已暂停 | 恢复 → 地址发现（§6.3）→ 返回目标 |
| 交互请求，本人沙箱已暂停、是旧模板、暂停前已回写（`gsdb-synced=1`） | 删除 → 同一请求内按新模板新建 |
| 闲置超过 `FUYAO_IDLE_SECONDS` | `fuyao-stop` → 暂停，metadata 记回写是否成功（`gsdb-synced`） |
| 闲置超过 `FUYAO_IDLE_SECONDS`、是旧模板 | `fuyao-stop --release` → 成功则删除（下次登录按新模板建）；失败则照旧暂停（`gsdb-synced=0`） |
| 暂停中、是旧模板、暂停前已回写 | 清扫器直接删除 |
| 暂停超过 `FUYAO_RETAIN_DAYS` | 暂停前已收尾回写（`gsdb-synced=1`）的删除；没回写成（或没记结果）的不删，记一次日志、`/admin/fuyao` 的 `unsynced_over_retention` 计数，交运维 |
| 运维 `/admin/fuyao/delete` | 在跑的先 `fuyao-stop --release`，成功才删；暂停的看 `gsdb-synced`；否则 409 不删，带 `force: true` 才强删（发版台冒烟工号固定带） |
| 设了 `FUYAO_SANDBOX_TIMEOUT`、离到期不到 15 分钟 | 在跑：`fuyao-stop --release` → 删除（有会话在跑的等到最后 5 分钟）；暂停中：暂停前已回写的删除，没回写成的记日志 |
| 转发连接失败 | 重新查询并重试一次；仍失败则按「沙箱不可用」重建 |

活动时间记在沙箱 metadata，两个网关副本共享，节流写入（同 `ACTIVITY_INTERVAL_SECONDS`）。

**换版**：发版只改 gateway-config 的 `FUYAO_*_TEMPLATE` 并滚动网关；已有沙箱按上表逐步换到新模板，
在跑且有人在用的不打断，没回写成功的不删。`/admin/fuyao` 的 `outdated` 是剩余的旧版沙箱数，发版台据此显示换版进度。

### 6.3 地址发现（2026-11-18 按现场实测改）

- **新建的沙箱**：`GET /v1/sandboxes/{id}/endpoints/49983` 给的就是它的地址。
- **恢复过的沙箱**（metadata `gsdb-resumed` = 恢复时刻）：平台 `/endpoints` 回的是暂停前的旧地址（实测），而旧地址可能已分给别人的新沙箱（Pod 网段地址会复用）。
  只认沙箱用自己的令牌向状态服务报到的来源地址（后台同步每 5 秒报到一次，状态服务记来源地址，实测是虚拟机的 Pod 网段地址），
  并且必须是**恢复之后**报上来的（记录距今秒数 ≤ 距恢复的时长 —— 刚暂停就恢复时，暂停前的记录还在 30 秒新鲜期内，也不能用）。
  问不到就等，每 0.5 秒问一次状态服务；**绝不往平台给的地址探活、跑启动器或收尾**。清扫器、运维接口同样只认报到的地址，问不到这一轮不动它（运维强删除外）。
- 恢复标记**先于**恢复写入：写不进就不恢复，避免恢复后的沙箱不带标记、被别的副本退回平台地址。
- 为什么「本人口令探活」不够兜底：探活本身就要把本人口令发到对方地址；补起会在对方虚拟机里写入本人令牌、接管本人目录独占。所以先保证地址可信，再探活。
- 第二道防线：沙箱里的启动器发现这台虚拟机已属于另一台沙箱（已有令牌、声明里的沙箱 ID 不同）就拒绝启动（退出码 6），什么都不改。

## 7. 状态服务

接口（HTTP，沙箱令牌放在 `Authorization: Bearer`）：

| 接口 | 说明 |
|---|---|
| `POST /v1/lease` | 按人加锁（带心跳续期），同一人同一时刻只有一个沙箱持有 |
| `GET /v1/state` | 载入：把本人目录里要本地化的部分打包返回 |
| `PUT /v1/state` | 增量写入：改动文件 + 删除清单；对话库为在线备份后的整库 |
| `POST /v1/state/finish` | 收尾：写入后清掉 dirty 标记 |
| `GET /v1/kb?since=<版本>` | 知识库只读副本（按版本增量） |
| `PUT /v1/kb` | 发布知识库（只限导入沙箱）：写互斥、原子替换、版本号加一 |
| `GET /v1/reports/...` | 报告只读（网关调用） |

写 NAS 沿用 `fdtree` 的规则（逐级不跟随链接、临时文件独占创建再原子改名），载入成功之前不传播删除，与现有 `statesync` 一致。

## 8. 模板

- `docker/Dockerfile.e2b`：以 runtime / kb-import 镜像为底，加启动器与占位文件（撑大磁盘，见 §2）；runtime 模板内置官方文档集。
  最后**压成一层**（`FROM scratch` + `COPY --from=… / /`）：模板构建服务解层时不处理 OCI whiteout（端到端实测：
  上层删掉的文件全回来，`.wh.*` 标记以 root 000 权限留在根文件系统，entrypoint 复制配置目录时失败），镜像配置照原样补回。
- `scripts/build-e2b-template.py`：在构建服务所在主机上——用 buildkit 构建派生镜像并导出成 OCI 目录 → `scripts/oci-serve.py` 只读端出（127.0.0.1）→ `/v3/templates` → `/v2/.../builds`（`fromImage` 指向本机）→ 等待就绪 → 停掉临时仓库。模板名带版本。
- `--from-oci`：构建服务所在主机不能上网时，镜像在别处按 `Dockerfile.e2b` 构建、导出成 OCI 包带过去，脚本只做端出与注册。
- 快照停在「待命」：只有 envd 与 systemd，没有任何用户身份。
- 平台方开放内部镜像仓库账号，或给构建服务补上根证书后，也可以改从仓库直接拉；脚本保留这条路。

## 9. 平台前提（上线前必须由平台落实）

| 前提 | 原因 |
|---|---|
| envd 需认证，或阻断虚拟机之间、普通 Pod 到虚拟机 envd 端口的访问 | 实测 envd 无认证，一个沙箱可以 root 身份在另一个沙箱里执行命令 |
| 宿主机侧限制沙箱出网，只放行凭据代理服务、状态服务 | 当前平台版本不能按沙箱下发出网规则，实测虚拟机出网不限 |
| OpenSandbox 开启认证 | 生产环境不得免认证 |
| 恢复后的地址可查询 | 见 §6.3 |

另有两条已知平台问题，我方已绕开、建议平台修复：模板构建不处理 OCI whiteout（§8，我方压层规避）；
模板构建服务重启后的第一次构建会一次补建约 300 个网络槽位，期间数百个 iptables 进程占满 CPU、
宿主机负载升到 300 左右，持续数分钟（端到端实测），同机其他服务的探活会超时。

## 10. 不变的部分

21 个技能的业务逻辑、根提示词、大盘前端、标准知识库安装、固定池化与按需模式的全部代码路径。

## 11. 实现顺序

1. 网关：OpenSandbox 客户端、envd 客户端、Fuyao 路由器与回收器、配置（含假 OpenSandbox / envd 的单元测试）；
2. 状态服务与 `statesync` 的 HTTP 后端；
3. 凭据代理网络形态与 GRMP 客户端网络模式；
4. 启动器与模板构建；
5. K8s 清单、发版台、手册；
6. 平台端到端验证。
