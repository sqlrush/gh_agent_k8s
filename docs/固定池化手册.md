# 固定池化手册

部署时固定建好一批 Pod，运行中不建、不删、不补；网关把每个人分到其中一个**槽位**。
与默认的**按需模式**（每人登录时现建一个 Pod）二选一，改网关的一个配置即可来回切，两种模式共用同一套 NAS 布局。

v1.2.0 里「由贵方平台管理预热沙箱」的形态已下线，由本手册的固定池化取代（池子改由我方网关调度，贵方平台只需做统一认证）。

## 0. 一页看懂

| 项 | 说明 |
|---|---|
| 规模 | `POOL_SIZE` 个 Pod（默认 16）× 每个 Pod `SLOTS_PER_POD` 个槽位（默认 8），满额 128 人同时在用 |
| 分配 | 在用人数不超过 Pod 数时**各自独占一个 Pod**；超过后分到在用人数最少的 Pod |
| 粘性保留 | 闲置 30 分钟（`POOL_IDLE_SECONDS`）转为**保留**：完整写回 NAS、停 opencode，文件留在槽位里；本人回来直接接着用 |
| 腾挪 | 保留 7 天（`POOL_RETAIN_DAYS`）没来、或需要给新人腾位置时，清空这个槽位给别人；本人下次登录从 NAS 载入，**不丢数据** |
| 满员 | 用户看到等待页，每 30 秒自动重试；同时把一位闲置超过 10 分钟（`POOL_EARLY_IDLE_SECONDS`）的在用者提前转保留，腾出的位置**预留**给等待的人 |
| 知识库导入 | 管理员的导入容器两种模式下都按需建，不进池子 |

进来要等多久（测试集群实测，3 个 Pod × 3 个槽位、真 opencode）：

| 情况 | 时间 |
|---|---|
| 本人已在用（另一个标签页、刷新） | 0 秒 |
| 回到自己的保留槽位 | 约 1–3 秒（起 opencode） |
| 新用户 / 槽位已腾挪 / Pod 重启过 | 约 3–4 秒，历史越大载入越久（500 MB 约多 5 秒） |
| 选中的 Pod 没有空闲槽位，要现场腾挪 | 再加一次容器重启：通常几秒；同一槽位 10 分钟内反复重启会因重启退避多等几十秒 |
| 满员时等别人提前转保留、交接给自己 | 约 7 秒（转保留 + 腾挪 + 绑定）；等不及时先看到等待页，30 秒后自动重试 |
| 对比：按需模式 | 6–7.6 秒 |

## 1. Pod 里面是什么

每个 Pod 有 `SLOTS_PER_POD` 个槽位容器和 1 个管家容器，同一个镜像（`gaussdb-agent-runtime`）。

| | 槽位 `slot-<i>` | 管家 `steward` |
|---|---|---|
| 跑什么 | 绑定后跑这个人的 opencode（模型 + 诊断技能）与报告服务；不在用时只有一个守护进程 | 载入、每 60 秒回写、转保留时完整写回、腾挪核验；控制接口 4098；**凭据代理**（给每个槽位加中间件与模型的凭据） |
| 运行身份 | uid 2000+i，组 1000（每个槽位 uid 不同） | uid 1000 |
| 挂什么 | 只有自己的盘（配置、状态、tmp、shm）、**只读**的共享知识库、管家给本槽位开的凭据代理套接字（只读） | NAS 上的全部用户目录、各槽位的状态盘、指令目录与套接字目录 |
| 端口 | 对话 4100+10i、报告 4101+10i、模型中继 4102+10i（只听 127.0.0.1） | 4098 |
| 密钥 | 本次绑定的口令、报告令牌（每次绑定 / 恢复都换）。**没有** GRMP 令牌、SM2 私钥、模型 Key | 控制密钥（Secret `sandbox-control`）、模型 Key（`model-api`）、SM2 私钥（`grmp-sm2`）；在用者的 GRMP 令牌（只在槽位在用期间，存在管家私有目录，0600） |

隔离靠什么：

| 风险 | 怎么挡 |
|---|---|
| 模型看全体用户的历史 | 槽位不挂 `users/`，只有管家挂；容器之间不共享进程空间 |
| 模型读凭据（`env`、`/proc/*/environ`、`opencode.json`） | 凭据根本不在槽位里（2026-10-23）：管家的凭据代理在转发时加上。每个槽位两个套接字：`credproxy.sock` 只转中间件，用这个槽位当前在用的人的令牌与工号，槽位不在用时一律拒绝；`model.sock` 只转模型。opencode 的工具权限另外拒掉 `env` / `printenv` / 读 `/proc`（见《参数手册》「工具权限」） |
| 同 Pod 别的槽位借我的身份调中间件 | 中间件套接字只挂进本槽位，不经任何 TCP 端口；本槽位的模型中继端口别人连得到，但那条路只转模型（全 Pod 同一个模型 Key） |
| 模型给自己换工号 | 指令目录在槽位里只读；控制接口签名，密钥不在槽位里 |
| 模型用链接诱使管家搬别人的文件 | 管家读写一律按文件描述符、逐级不跟随链接 |
| 同 Pod 别的槽位读我的文件 / 看我的进程 | 各自的盘、各自的进程空间；根文件系统只读 |
| 同 Pod 共用 localhost | 对话端口每次绑定换口令；报告端口要报告令牌；口令与令牌只在网关，不到浏览器 |
| 同 Pod 别的槽位抢我的端口冒充我 | 不跑 opencode 时槽位自己占着对话 / 报告端口，模型中继端口从启动起一直占着；管家按监听者的 uid 核对这三个端口，发现冒充者即告警、停止转发、腾挪肇事槽位 |
| 上一个人留下的进程与文件 | 腾挪 = 重启槽位容器：所有进程随之结束；新起的 1 号进程**先清盘**再做别的；网关拿 k8s 的容器 ID 核对确实重启过 |
| 同一个人同时进两个槽位 | NAS 上的独占标记 |
| 数据库权限 | 每次绑定 / 恢复由网关把本人的 GRMP 令牌（Secret `grmp-token-<工号>`）加密交给管家；转保留、腾挪时清掉 |

## 2. 一次性部署

### 2.1 前提

- 按需模式能跑通（《部署手册》阶段 0–5）：命名空间、NAS（`users/` 属主 1000:1000）、`agent-config`、Secret `model-api`、每人一个 `grmp-token-<工号>`。
- CNI 支持 NetworkPolicy（Calico / Cilium 等）。

### 2.2 控制密钥

网关与各 Pod 的管家共用一把，至少 16 个字符：

```bash
kubectl -n gaussdb-agent create secret generic sandbox-control --from-literal=KEY="$(openssl rand -hex 32)"
```

### 2.3 渲染并部署池子

Pod 里的容器数等于槽位数，所以清单由脚本渲染（只用 Python 标准库）：

```bash
python3 k8s/tools/render-pool.py --image <仓库前缀>/gaussdb-agent-runtime:<版本> \
    --pool-size 16 --slots-per-pod 8 \
    --grmp-cidr <中间件网段> --grmp-port <中间件端口> --model-cidr <模型服务网段> --model-ports 443 \
    > pool.yaml
kubectl apply -f pool.yaml
kubectl -n gaussdb-agent get pods -l app=gaussdb-agent,role=pool     # 每个 Pod 应为 9/9 Running
```

`pool.yaml` 含 StatefulSet `agent-pool`、headless Service、PodDisruptionBudget 与两条 NetworkPolicy
（`pool-policy`：池子只接受网关的连接；`gateway-to-pool`：网关可以连池子）。参数见第 4.1 节。

### 2.4 网关切到固定池化

改 ConfigMap `gateway-config`，重启网关：

```bash
kubectl -n gaussdb-agent patch configmap gateway-config --type merge -p '{"data":{"RUNTIME_MODE":"pool"}}'
kubectl -n gaussdb-agent rollout restart deploy/gateway
```

网关日志应出现「诊断容器 固定池化(app=gaussdb-agent,role=pool)」。其余参数见第 4.2 节。

### 2.5 验证

```bash
curl -s -H "X-Admin-Token: <运维密钥>" http://<网关>/admin/pool    # 每个 Pod reachable,槽位 free
```

用一个工号经统一认证登录：第一次约 3–4 秒进入对话页；`/admin/pool` 里能看到他占了一个槽位（state `active`）。

## 3. 资源

```
集群预留 = POOL_SIZE × (SLOTS_PER_POD × 槽位 request + 管家 request)
默认    = 16 × (8 × 100m / 768Mi + 50m / 64Mi) ≈ 13.6 CPU / 97 GiB
```

- 槽位 request 默认 768Mi：真实使用每人 0.7–0.9 GiB；上限默认 2 CPU / 2Gi，可以超卖，按实际并发评估节点数。
- 保留状态的人已停 opencode，几乎不占内存与 CPU，占的是这个槽位的盘（`--slot-state-size`，默认 4Gi）。
- 一个 Pod 8 人满载约 5.6 GiB；8 个空闲 opencode 约 2 GiB。

## 4. 参数

### 4.1 渲染参数（`k8s/tools/render-pool.py`）

| 参数 | 默认 | 说明 |
|---|---|---|
| `--image` | （必填） | 运行时镜像，与按需模式同一个 |
| `--image-pull-policy` | `IfNotPresent` | |
| `--namespace` | `gaussdb-agent` | |
| `--pool-size` | 16 | Pod 数（1–64） |
| `--slots-per-pod` | 8 | 每个 Pod 的槽位数（1–16） |
| `--users-subpath` | `users` | NAS 上用户目录的上一层，与按需模式一致 |
| `--nas-claim` | `nas` | NAS 的 PVC 名 |
| `--slot-cpu-request` / `--slot-memory-request` | `100m` / `768Mi` | 每个槽位的预留 |
| `--slot-cpu-limit` / `--slot-memory-limit` | `2` / `2Gi` | 每个槽位的上限 |
| `--slot-state-size` | `4Gi` | 每人在槽位里的文件上限（对话库、工作目录、报告） |
| `--steward-memory-limit` | `512Mi` | 管家的内存上限 |
| `--grace-seconds` | 180 | 删 Pod 时的宽限期：管家要把所有在用的槽位并行完整写回 |
| `--runtime-class` | 空 | 集群有 gVisor / Kata 时填 runtimeClassName，整 Pod 启用 |
| `--grmp-cidr` / `--grmp-port` | `10.0.0.0/8` / 8080 | 槽位能连的中间件地址 |
| `--model-cidr` / `--model-ports` | `10.0.0.0/8` / `443,80` | 槽位能连的模型服务地址 |
| `--egress` | 无 | 额外的出站目标，可重复，如 embedding 服务 `10.1.2.3/32:11434` |
| `--test-override` | 无 | **只给测试集群**缩短时长；渲染结果会带标签 `gaussdb-agent/test-overrides`，正式部署不要用 |

改了参数：重新渲染、`kubectl apply`，再**逐个**删 Pod 让它按新清单重建（StatefulSet 是 `OnDelete`，不会自动滚动；
删 Pod 时在用的人先完整写回，下次请求自动分到别的槽位）。

### 4.2 网关参数（ConfigMap `gateway-config`）

| 键 | 默认 | 下限 | 说明 |
|---|---|---|---|
| `RUNTIME_MODE` | `ondemand` | | `pool` = 固定池化 |
| `POOL_SELECTOR` | `app=gaussdb-agent,role=pool` | | 池子 Pod 的标签，与渲染脚本一致 |
| `POOL_IDLE_SECONDS` | 1800 | 300 | 在用多久没有交互（也没有会话在跑）就转保留 |
| `POOL_EARLY_IDLE_SECONDS` | 600 | 60 | 满员时，闲置超过这么久的在用者可被提前转保留；不能长于上一项 |
| `POOL_RETAIN_DAYS` | 7 | 1 | 保留多少天没来就腾挪 |
| `POOL_FREE_SLOTS` | 1 | 0 | 每个 Pod 后台至少留几个空闲槽位给新人 |
| `POOL_SWEEP_SECONDS` | 30 | 5 | 后台多久一轮：报活动、转保留、腾挪、核验 |
| `POOL_WAIT_SECONDS` | 60 | 10 | 一次请求为分配最多等多久，等不到回等待页 |

控制密钥由 `gateway.yaml` 从 Secret `sandbox-control` 读，不在 ConfigMap 里。低于下限、`RUNTIME_MODE` 不认识、
池化模式没有控制密钥时，网关拒绝启动。

**什么算「在用」**：用户的交互请求（打开页面、发消息、看报告）与正在跑的会话。opencode 网页开着时每 10 秒的探活和
一直挂着的事件流**不算** —— 否则开着的标签页永远不闲置；这两类请求也不会把转保留的槽位拉回来，下一次真正的操作才会。

### 4.3 固定不变的几项

在用时每 60 秒回写一次 NAS（与按需模式的 `STATE_SYNC_SECONDS` 相同）；绑定时等 opencode 就绪最多 60 秒；
转保留时等槽位确认停下最多 40 秒；腾挪后 360 秒内核验不通过的槽位转为停用（kubelet 的重启退避最长 5 分钟）。

## 5. 数据：存什么、丢什么

| 情况 | 结果 |
|---|---|
| 闲置转保留、删 Pod（`kubectl delete pod`）、节点排空 | **不丢**：停 opencode、最终快照、完整写回之后才算完成 |
| 节点故障、OOM、容器被强杀 | 最多丢最近一个回写周期（60 秒）；下次登录从 NAS 载入，上次那份先快照到用户目录下的 `.unclean-<时间>/`，提示「上次非正常退出」 |
| 写回 NAS 失败（NAS 满了 / 不可写） | 这个保留槽位继续持有独占、不会被腾挪，后台每个周期重试并告警；本人回来回到同一个槽位，用的是最新的文件 |
| 本人在别处（另一个槽位、按需模式的 Pod）用过 | 回到保留槽位前核对版本令牌与主库指纹，对不上就作废这份副本，从 NAS 重新载入 |

## 6. 运维

### 6.1 看池子与手动操作

控制 API（与 `/admin/pods` 同一个运维密钥）：

```bash
H="X-Admin-Token: <运维密钥>"
curl -s -H "$H" http://<网关>/admin/pool                                     # 整池:每个槽位的状态、工号、监听者
curl -s -H "$H" -d '{"pod":"agent-pool-3","slot":2}' http://<网关>/admin/pool/retain    # 转保留(写回、停 opencode)
curl -s -H "$H" -d '{"pod":"agent-pool-3","slot":2}' http://<网关>/admin/pool/evict     # 腾挪(只能对保留 / 空闲 / 停用的)
curl -s -H "$H" -d '{"pod":"agent-pool-3","slot":2}' http://<网关>/admin/pool/verify    # 腾挪后手动核验
curl -s -H "$H" -d '{"pod":"agent-pool-3","slot":2,"reason":"排查"}' http://<网关>/admin/pool/disable   # 停用
```

槽位状态：`free` 空闲、`binding` 绑定中、`active` 在用、`retaining` 转保留中、`retained` 保留、`resuming` 恢复中、
`evicting` 清理中、`disabled` 停用、`booting` 刚启动还没握手。返回里没有任何口令与令牌。

### 6.2 常见操作

| 要做什么 | 怎么做 |
|---|---|
| 维护某个节点 | `kubectl drain`：PDB 保证一次最多一个池子 Pod 不可用；被驱逐的 Pod 先完整写回 |
| 重建某个 Pod | `kubectl delete pod agent-pool-<n>`（不要 `--force --grace-period=0`） |
| 升级镜像 / 改资源 / 改槽位数 | 重新渲染、`kubectl apply`、逐个删 Pod |
| 扩容 | `--pool-size` 调大、重新渲染并 apply，新 Pod 就绪即参与分配 |
| 缩容 | 先对编号最大的那几个 Pod 上的人逐个 `retain`，再调小 `--pool-size` 并 apply |
| 轮换控制密钥 | 改 Secret → 重启网关 → 逐个删池子 Pod |
| 切回按需模式 | `RUNTIME_MODE=ondemand` 并重启网关；池子 Pod 可以删掉（删时在用的人先完整写回） |
| 槽位停用了 | 看管家日志（`kubectl logs agent-pool-<n> -c steward`）：腾挪后容器没按时重启、或重启后核验不过；处理后 `verify`，或删这个 Pod 重建 |

## 7. 残余风险

写进交付文档，请贵方知悉：

- **同 Pod 的槽位共用内核与网络命名空间**，隔离强度低于「不同 Pod」。抽象 Unix 套接字没有权限控制（opencode 与技能都不使用）。
  集群有 gVisor / Kata Containers 时用 `--runtime-class` 整 Pod 启用。
- **opencode 崩溃重启的约 2.5 秒里，它的端口是空着的**（opencode 不能接管槽位守护进程占着的端口）。同 Pod 的恶意槽位在这期间
  抢到端口时，管家几秒内发现、定位到肇事槽位并腾挪它，网关停止转发；在那之前，本人的下一个请求可能落到冒充者手里。
- **模型仍能以本人身份调用中间件白名单接口、使用模型**：它能直接连本槽位的凭据代理，做的事与经技能能做的相同，只是拿不到凭据本身。
  工号由代理按绑定写入，换不了人。
- **一个 Pod 里最多 `SLOTS_PER_POD` 个人共享这个 Pod 的资源上限**；某个人跑满 CPU 会影响同 Pod 的人（每个槽位有各自的 limits）。

## 8. 排查

| 现象 | 看什么 |
|---|---|
| 网关日志「管家暂时连不上」 | 池子 Pod 是否 Running；网关 Pod 的标签是否 `app=agent-gateway`（`pool-policy` 只放行它） |
| 等待页一直不消失 | `/admin/pool`：是不是所有槽位都在用；有没有大量 `disabled` 槽位 |
| 网关日志 `held_elsewhere:runtime-<工号>-…` | 这个人还有一个按需模式的 Pod 持有独占（刚从按需切过来）：等它闲置回收，或删掉那个 Deployment |
| 管家日志「外来监听者」「冒充」 | 某个槽位在别的槽位的端口上监听：网关会自动腾挪肇事槽位；同一个工号反复出现请人工核查 |
| 绑定失败 `port_squatted` | 同上，这次绑定落到了被冒充的槽位上；用户重试会分到别的槽位 |
| 浏览器里事件流或探活返回 503 `not_active` | 正常：这个人的槽位已转保留，下一次操作会自动恢复 |
