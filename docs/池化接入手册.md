# 池化接入手册：由贵方平台管理的预热沙箱

适用版本：v1.2.0 起。本手册讲**第二种部署形态**——贵方平台自己维护一池预先启动好的沙箱，
用户登录时分配一个、退出时回收。第一种形态（我方网关按工号建 Pod，见《接入手册-SSO与K8s》）不受影响，两者可以并存。

---

## 0. 先看这一页

**用法**：集群启动时贵方平台先建好 16 个沙箱；用户登录就占一个，第 17 个人来了再现建一个；
有人退出就回收，回收到总数 16 为止。

**我方提供**：沙箱镜像（与网关模式同一个 `gaussdb-agent-runtime`）、沙箱 Pod 模板、三个控制接口、平台参考实现。
**贵方平台负责**：池子数量、工号 → 沙箱的映射、倒计时、补建、口令保管、反向代理。

```
浏览器 / CLI ──► 贵方平台(SSO · 池子 · 映射 · 倒计时 · 反向代理)
                    │  bind / unbind / status          │ 对话(注入口令)    │ 报告
                    ▼  :4098 + 控制密钥                 ▼ :4096             ▼ :4097
            ┌──────────────── 沙箱 Pod(每个沙箱一个,用完即换) ────────────────┐
            │  副容器 poolctl:载入 · 每 60 秒回写 · 收尾回写 · 独占             │
            │  主容器 sandbox:opencode + 17 个诊断技能,看不到任何人的 NAS 目录 │
            └────────────────────────────────────────────────────────────────┘
                    │ 只读写绑定工号的目录                    │ 只读
                    ▼                                         ▼
               NAS users/<工号>/                         NAS kb/(共享知识库)
```

**一个沙箱一生只服务一个人。** 用户退出后，平台删除这个沙箱，总数不足 16 就补建一个新的。
用户感受与「循环使用」一样（登录总能拿到预热好的沙箱），但前一个人的文件、后台进程不可能留给下一个人。

| 时刻 | 事件 | 使用中 | 空闲 | 总数 | 平台动作 |
|---|---|---|---|---|---|
| t0 | 集群启动 | 0 | 16 | 16 | 预建 16 个 |
| t1 | 16 人陆续登录 | 16 | 0 | 16 | 逐个绑定 |
| t2 | 第 17 人登录 | 17 | 0 | 17 | 现建 1 个再绑定，这个人多等几秒 |
| t3 | 2 人退出 | 15 | 1 | 16 | 删 2 个，总数 15 不足 16，补建 1 个 |

**本地实测**（OrbStack k8s，镜像已在节点上，2026-10-14）：16 个沙箱从创建到全部就绪 6～7 秒；平台发起一次登录
（查空闲 + 绑定，含载入历史、启动 opencode、确认就绪）约 2 秒——这是经 kubectl port-forward 测的，集群内直连还会少掉这部分开销；
没有空闲、现建再绑定约 5～6 秒。

## 1. 沙箱里面是什么

一个沙箱 = 一个 Pod，两个容器，**同一个镜像**、不同入口：

| | 主容器 `sandbox` | 副容器 `poolctl` |
|---|---|---|
| 跑什么 | opencode 与 17 个诊断技能；模型在这里执行命令 | 控制接口、状态载入与回写，只跑我方代码 |
| 能看到的 NAS | 只有 `kb/`（只读） | 只有 `users/`（读写） |
| 秘密 | 共用 GRMP 令牌、模型 key、向量库只读口令 | 控制密钥（**只在这里**） |
| 端口 | 4096 对话、4097 报告 | 4098 控制 |

空闲时 opencode 不运行（4096 不监听）。平台误把用户路由到空闲沙箱只会连接失败，不会进入一个无主的会话。

**为什么要两个容器**：沙箱在知道用户是谁之前就启动了，而运行中的 Pod 不能再加挂载——
只能让一个挂着全部 `users/` 的组件在绑定时把这个人的历史搬进来。这个组件绝不能和「能执行命令的模型」在同一个容器里，
否则一句「列一下 /nas 下的目录」就能看到所有人的历史。

## 2. 一次性部署

前提：《部署手册》的基础资源已就位（命名空间、NAS 的 PV/PVC、`agent-config`、`model-api`、向量库）。

**① NAS 上的 `users/` 必须属于 uid 1000**

```bash
# 在 NFS 服务器上(只做一次)
mkdir -p /export/gaussdb-agent/{users,admins,kb}
chown -R 1000:1000 /export/gaussdb-agent
```

没做这一步，副容器连用户目录都建不出来，bind 会回 500，`reason` 是 `users_not_writable`，`message` 里写明当前属主。

**② 两个 Secret**

```bash
NS=gaussdb-agent
# 控制密钥:平台调 4098 时放在请求头 X-Sandbox-Key;只注入副容器
kubectl -n $NS create secret generic sandbox-control --from-literal=KEY="$(openssl rand -hex 32)"
# 共用的中间件令牌(池化下全体共用一个;工号仍会随请求发给中间件)
kubectl -n $NS create secret generic grmp-token --from-literal=GRMP_AUTH_TOKEN='<令牌>'
```

控制密钥至少 16 个字符；副容器拿不到它会拒绝启动。

**③ 网络策略**

`k8s/base/networkpolicy.yaml` 里的 `sandbox-policy`：4096 / 4097 / 4098 的入站只放行带标签 `gaussdb-agent/platform: "true"`
的 Pod 或命名空间。请给贵方平台的 Pod（或它所在的命名空间）打上这个标签，或者把选择器改成贵方平台已有的标签。
出站规则与网关模式的用户 Pod 相同，地址段按实际填写。**集群的网络插件必须执行 NetworkPolicy**（Calico、Cilium 等）。

```bash
kubectl apply -f k8s/base/networkpolicy.yaml
```

**④ 沙箱模板**

`k8s/templates/sandbox.yaml`，三个占位符：

| 占位符 | 填什么 |
|---|---|
| `${SANDBOX_ID}` | 平台给的编号，只能小写字母、数字、`-`；Pod 名为 `sandbox-<编号>` |
| `${IMAGE}` | `gaussdb-agent-runtime:<版本>`（贵方仓库前缀按实际加） |
| `${IMAGE_PULL_POLICY}` | 一般 `IfNotPresent` |

模板请**原样使用**，只填占位符。下面几项是隔离的物理保证，改了就不再成立：

- 两个容器**不共享进程空间**（不要加 `shareProcessNamespace: true`）——共享后主容器能经 `/proc` 读到副容器挂的全部用户目录与控制密钥；
- 只有副容器挂 `users/`，只有副容器有控制密钥；主容器的指令目录是只读挂载；
- 两个容器都是只读根文件系统、禁止提权、去掉全部特权；不挂 ServiceAccount 令牌；
- `terminationGracePeriodSeconds: 90`——删除沙箱时副容器要把最后一段对话写回 NAS。

用的是**裸 Pod**，不是 Deployment / StatefulSet：沙箱生死由平台决定。Deployment 会在 Pod 消失时自己补建，与平台的补建叠加就多出沙箱。

## 3. 平台要做的事（对接契约）

1. **维护池子**：启动时按模板建 16 个；总数不少于 16；用户超出时现建。
2. **分配**：同一工号若已有沙箱（包括倒计时中的）必须接回原沙箱——**同一个人同一时刻只能有一个沙箱**；没有才取一个空闲的调 `bind`。
3. **转发**：浏览器 → 沙箱 4096，注入 Basic `opencode:<口令>`；口令只留在平台，**不下发到浏览器**。流式转发必须关闭缓冲、不设读超时。
   大盘的 `/reports/*` 转到该用户沙箱的 4097（去掉前缀）。
4. **倒计时**：用户关了浏览器不立即退出。建议以「该用户到平台的最后一条连接断开」起算——opencode 的 Web 页面开着时始终挂着一条事件流，页面关了它就断。重新连上即取消倒计时。
5. **点退出**：立即调 `unbind`。
6. **回收**：`unbind` 返回后删除这个 Pod（正常删除，**不要** `--force --grace-period=0`）；总数不足 16 就补建。退役的沙箱不要再分配。
7. **失败处理**：`bind` 返回 500 / 504 → 删掉该沙箱、换一个重试；`unbind` 返回 500 或连接断开 → 照样删除并告警。
8. **知识库管理员**的导入容器不进池，仍按网关模式的方式按人创建。

参考实现：`scripts/k8s/pool-sim.py`（池子、映射、倒计时、补建、返回码分支都在里面，可直接对照）。

## 4. 控制接口（副容器，端口 4098）

除 `/healthz` 外，所有请求都要带 `X-Sandbox-Key: <控制密钥>`；不对回 401，不说明原因。

### 4.1 绑定

```http
POST /sandbox/bind
X-Sandbox-Key: <控制密钥>
Content-Type: application/json

{"user_id": "u1234"}
```

成功（200）：

```json
{
  "sandbox": "sandbox-07",
  "state": "bound",
  "user_id": "u1234",
  "opencode": {"port": 4096, "username": "opencode", "password": "<本次随机生成>"},
  "reports_port": 4097,
  "loaded": {"files": 45, "dbs": 1, "mb": 3.2, "seconds": 0.4, "unclean_last_time": false, "selfcheck": "ok"}
}
```

| 返回码 | 含义 | 平台该怎么做 |
|---|---|---|
| 200 | 已绑定。对**同一工号**重复调用是幂等的，返回同样内容 | 记下口令，开始转发 |
| 400 `bad_user_id` | 工号格式不对（小写字母、数字、`-`，最长 54 位；会先转小写） | 检查 SSO 给的工号 |
| 401 | 控制密钥不对 | — |
| 409 `state` | 这个沙箱已绑定别人 / 正在绑定 / 已退役 | 换一个空闲沙箱 |
| 409 `owner_busy` | 这个工号的目录正被另一个沙箱持有。响应带 `holder`（持有者 Pod 名）与 `retry_after`（秒）。**本沙箱保持空闲**，可以分给别人 | 该工号还有活着的沙箱 → 接回它；没有 → 上一个沙箱多半是被强杀的，等 `retry_after` 秒再绑定（最长 90 秒） |
| 500 / 504 | 载入失败或 opencode 未在时限内就绪。**沙箱已退役**；`reason` 说明是哪一步 | 删掉它，换一个空闲沙箱重试 |

`unclean_last_time: true`：这个人上次是非正常退出（沙箱被强杀、节点故障），最后不到一分钟的对话可能已丢失；平台可以选择提示用户。

### 4.2 解绑

```http
POST /sandbox/unbind
X-Sandbox-Key: <控制密钥>
Content-Type: application/json

{"user_id": "u1234", "reason": "logout"}
```

`reason` 取 `logout`（点退出）/ `timeout`（倒计时到点）/ `admin`（运维操作），只用于日志。
`user_id` 必须与当前绑定的工号一致，否则 409——防止平台映射出错时解绑了别人。

| 返回码 | 含义 | 平台该怎么做 |
|---|---|---|
| 200 | 已完整写回 NAS，沙箱已退役。`aborted_running` 表示停止前是否有正在跑的对话被中止 | 删除 Pod，按需补建 |
| 409 | 工号不一致，或沙箱不在「使用中」 | 核对映射表，**先别删** |
| 500 | 收尾不完整（`reason`：`stop_not_confirmed` 或 `sync_errors`）。已尽量写回，非正常退出标记保留，下次绑定会提示。**沙箱同样已退役** | 照样删除 Pod；告警给运维 |

解绑的时间主要花在停 opencode 与写回上，历史不大时是秒级；最长约 50 秒（等主容器停下的时限 40 秒）。

### 4.3 状态与探针

- `GET /sandbox/status` → `{"sandbox", "state", "user_id", "bound_at", "last_sync_at", "last_sync"}`，**不返回口令**。
  `state` 取 `idle` / `binding` / `bound` / `unbinding` / `retired`。
- `GET /healthz` 不鉴权，只回 `{"ok": true}`，不带任何用户信息。模板里它是副容器的就绪探针：Pod 就绪 = 可以分配。

### 4.4 绑定之后怎么对话

与网关模式完全相同：opencode 1.18.27 的 HTTP API，Basic 认证，用户名 `opencode`，口令取绑定响应里的 `password`。

```bash
B=http://<沙箱 Pod IP>:4096
A="-u opencode:<口令> -H Content-Type:application/json"
curl $A -d '{"title":"慢SQL排查"}' $B/session                     # 建会话
curl $A -d '{"parts":[{"type":"text","text":"登录 10.0.0.9 的 postgres 库,看下最近的慢 SQL"}]}' \
     $B/session/<会话 id>/message                                   # 同步,模型跑完才返回
curl $A $B/session                                                  # 会话列表(含以前沙箱里的历史)
```

## 5. 数据：存什么、丢什么

NAS 上每个人的目录结构与网关模式**完全相同**：同一个人可以在两种形态之间切换，数据不需要迁移。

| 内容 | 结论 |
|---|---|
| 对话记录、模型上下文、工作目录文件、撤销快照、技能报告、数据库登录句柄 | 持久化。下次登录分到另一个沙箱也能看到并接着聊（本地实测：退出再登录后，模型记得上一句） |
| 使用中 | 每 60 秒写回一次 NAS；对话库自上次以来没变就不重写 |
| 点退出 / 倒计时到点 / 平台正常删除沙箱 | 先中止正在跑的那一轮（已写出的部分保留），再完整写回 NAS。**零丢失** |
| 沙箱被强杀、节点故障 | 最多丢最近 60 秒。下次绑定时 `unclean_last_time: true`，NAS 上留一份当时的快照（`.unclean-<时间>`） |
| `/tmp`、主目录下的临时文件 | 不保留 |

## 6. 安全边界

| 风险 | 怎么挡 | 本地实测 |
|---|---|---|
| 模型读别人的历史 | 主容器不挂 `users/`；只读挂 `kb/` | 主容器里 `ls /nas` 只有 `kb`，`/pool` 不存在 |
| 模型调控制接口给自己换工号 | 控制密钥只在副容器；两容器不共享进程空间 | 主容器里不带密钥调 4098 回 401；`/proc` 里找不到密钥；看不到副容器的进程 |
| 模型改指令伪造身份 | 指令目录在主容器只读；副容器只认接口传入的工号 | 写指令目录报只读 |
| 模型在工作目录放符号链接，诱使副容器把别人的文件搬进来 | 副容器读写一律按文件描述符、逐级不跟随链接，打开后再确认是普通文件；库只搬主容器生成的快照 | 埋了指向别人库、指向全部用户目录、指向副容器自身环境的三条链接，退出后一条都没上 NAS |
| 模型拿 k8s 凭据 | 沙箱不挂 ServiceAccount 令牌 | 令牌目录不存在 |
| 外部或其他沙箱直连沙箱端口 | `sandbox-policy`：入站只放行平台 | 带平台标签的 Pod 能到 4098；不带的到不了；沙箱之间互相到不了 |
| 前一个人的残留 | 用完即换，沙箱不复用 | 退役的沙箱再 bind 回 409 |
| 同一个人同时进两个沙箱 | NAS 上的独占标记 | 第二个沙箱 bind 同一工号回 409 `owner_busy`，且该沙箱仍空闲 |

**我方挡不住、需要贵方知悉的**

- **共用中间件令牌**：池化下所有人的数据库权限相同；工号随请求发给中间件，按人授权只能在中间件侧做。
- **普通容器与宿主机共用内核**：模型能执行命令，内核漏洞可能导致逃逸。贵方集群若提供 gVisor 或 Kata Containers，
  在模板里取消 `runtimeClassName` 那一行的注释即可启用。
- **大盘只在用户有沙箱时有数据**：报告端口在沙箱里，用户退出后大盘看不到（网关模式会自动拉起 Pod，池化不会）。

## 7. 需贵方确认的事项

| # | 事项 | 我方当前做法 |
|---|---|---|
| 1 | 倒计时时长，以及平台怎么判断浏览器已关 | 建议 30 分钟，以最后一条连接断开起算；倒计时内回来接回原沙箱 |
| 2 | 池子的上限（超过 16 后最多建几个） | 平台侧参数。每个沙箱的上限：主容器 2 CPU / 2 GiB，副容器 0.5 CPU / 256 MiB；请求值合计 0.3 CPU / 576 MiB |
| 3 | 是否使用四个大盘 | 若使用，平台需按 §3 第 3 条路由 `/reports/*` |
| 4 | 是否提供 gVisor / Kata | 有就启用；没有不影响功能，但记为残余风险 |
| 5 | 安全审查是否要求副容器用单独的最小镜像 | 默认与主容器同一镜像（少交付、少审查一个镜像；同步代码与 opencode 永远同一版本）；要求时再拆 |
| 6 | 是否需要「清空后复用同一个沙箱」 | 本版不提供，一律用完即换。用户感受相同；需要时另行评估 |
| 7 | 长期使用后历史变大 | 本版对话库没变就不回写；超过一定天数的会话自动归档需贵方确定天数后再开启 |

## 8. 排查

```bash
NS=gaussdb-agent
kubectl -n $NS get pods -l role=sandbox -o wide                    # 池子全貌
kubectl -n $NS logs sandbox-<编号> -c poolctl --tail=50             # 绑定、回写、收尾的每一步
kubectl -n $NS logs sandbox-<编号> -c sandbox --tail=50             # 守护进程与 opencode
curl -s -H "X-Sandbox-Key: $KEY" http://<Pod IP>:4098/sandbox/status # 状态(不含口令)
```

| 现象 | 先看 |
|---|---|
| bind 回 500 `users_not_writable` | NAS 上 `users/` 属主不是 1000，见 §2 ① |
| bind 回 409 `owner_busy` 一直不消失 | `holder` 那个 Pod 是否还活着；活着说明平台映射表漏了这个人，应接回它 |
| bind 回 504 `opencode_not_ready` | `-c sandbox` 的日志；多为模型配置（`agent-config`、`model-api`）不全 |
| 平台连不上 4098 | 平台的 Pod 有没有 `gaussdb-agent/platform: "true"` 标签；网络插件是否执行 NetworkPolicy |
| 用户说「上次的对话少了最后几句」 | 那次绑定的 `unclean_last_time` 是否为 true；NAS 上 `users/<工号>/.unclean-*` 是当时的快照 |
