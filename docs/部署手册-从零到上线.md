# 部署手册：从零到上线

> 面向：负责实施的运维工程师。
> 用法：**从头到尾照做**。每一步都给了「怎么验证成功」与「失败了看哪里」。
> 全程约 3–5 小时（不含网络申请、密钥审批、SSO 侧改动的等待时间）。
>
> 架构与设计说明见 [`接入手册-SSO与K8s.md`](./接入手册-SSO与K8s.md)。本篇只讲**怎么做**。
>
> 本篇按默认的**按需模式**写（每人登录时现建 Pod）。要部署时固定建好一批 Pod、按槽位分配的**固定池化**，
> 本篇阶段 0–5 照做，之后按 [`固定池化手册.md`](./固定池化手册.md) §2 渲染并部署池子、把网关切到 `RUNTIME_MODE=pool`。

## 阶段 0：开工前的清单

### 0.1 需要提前拿到的东西

逐项确认，**缺任何一项都会在中途卡住**：

- [ ] **K8s 集群**访问权限，能在目标命名空间建 Deployment / Service / Secret / ConfigMap / NetworkPolicy / ServiceAccount / Role / RoleBinding
- [ ] **CNI 支持 NetworkPolicy**（Calico / Cilium 等）。不确定就问集群管理员，**不要假设**
- [ ] **RWX 存储**（NFS v4.1），容量按 `人数 × 3 GB + 知识库 20 GB` 估
- [ ] **内网镜像仓库**地址与推送权限
- [ ] **模型服务**：地址（OpenAI 兼容，含 `/v1`）、密钥、模型 id
- [ ] **embedding 端点**：地址、模型名、维度 —— 见 §0.3，**这一项最容易被漏**
- [ ] **GRMP 中间件**：地址、端口；以及**按人签发令牌的获取方式**
- [ ] **中间件白名单已导入本版本的诊断脚本**（`agent-v1.4.3` 共 128 条；首次导入用全量 `scripts.sql`，
      已导入过上一版 126 条的导增量 `scripts-delta-20261030.sql`，更早的按 §10.5 第 0 步）。这一步由中间件团队做
- [ ] **SSO 侧**：能在转发时注入请求头的位置（网关 / WAF / Ingress）
- [ ] 一台能执行 `kubectl` 与 `docker` 的跳板机

### 0.2 命名约定

本手册全程使用：

| 项 | 值 | 改了要一起改的地方 |
|---|---|---|
| 命名空间 | `gaussdb-agent` | 所有清单 + `GATEWAY_NAMESPACE` |
| 镜像仓库 | `registry.内网/gaussdb-agent` | 所有清单的 `image:` 字段 |
| 版本标签 | `agent-v1.4.3-oc1.18.27` | `gateway-config.USER_IMAGE_TAG` + 网关与大盘前端的 `image:`（清单里已是这个标签，升级时三处一起改） |

### 0.3 embedding 端点：现在就去确认

**这是唯一一项「前置时间可能以周计」的依赖**，其余都能当天解决。

> 请贵方模型服务团队回答：**是否提供 OpenAI 兼容的 `/v1/embeddings` 接口？**

embedding 模型与对话模型是两种模型。模型服务跑的是 Qwen 之类的对话模型时，
`/v1/embeddings` 往往直接 404（vLLM 装一个对话模型就是这样）。

- **有** → 记下模型名与维度，阶段 5 用
- **没有** → 需要另外部署一个（Xinference / Ollama 等，装 `bge-m3` 之类），**现在就去申请**
- **暂时没有也能上线** → 知识库只做关键词检索（状态行「向量:未启用」），功能可用但语义检索弱；后补即可，不阻塞

### 0.4 数据库侧：事后分析能回看多久（由贵方 DBA 评估开启）

**不阻塞部署**，但决定上线后「事后」能查到什么：隔天按 sql_id 调优、回看某个时段的体检 / Top SQL / WDR，
用的都是数据库自己留下的记录。下面三类参数请贵方 DBA 评估后开启或调整，我方不改数据库参数。

| 参数 | 默认值 | 推荐值 / 上限 | 影响事后分析的什么 |
|---|---|---|---|
| `track_stmt_retention_time` | `3600,604800` | **`86400,604800`**（两项都已是上限） | 格式「全量 SQL 秒数,慢 SQL 秒数」。全量那一项决定隔天还能不能按 sql_id 取到**普通语句**的文本与历史执行计划；慢 SQL 能留 7 天 |
| `enable_asp` | `on` | 保持 `on` | 活跃会话采样（ASP）总开关。下一版本的「时段锁回溯」靠 `gs_asp` 事后还原阻塞链 |
| `asp_sample_interval` | `1`（秒） | 保持默认 | 采样间隔 |
| `asp_flush_rate` | `10` | 保持默认 | 约每 10 秒落一次 `gs_asp` 表 —— 事后能看到的粒度约 10 秒，**更短的锁等待可能采不到** |
| `asp_retention_days` | `2`（天） | 按要回看几天的锁调大 | `gs_asp` 保留几天，就能回看几天的锁 |
| `enable_wdr_snapshot` | `off`（openGauss；GaussDB 以所用版本为准） | `on` | WDR 快照总开关。时段体检、时段 Top SQL、WDR 报告都用快照 |
| `wdr_snapshot_interval` | `60`（分钟） | 保持默认；要对齐更细的时段可调小 | 快照间隔决定时段分析能对齐到多细 |
| `wdr_snapshot_retention_days` | `8`（天） | 按要回看多久调大 | 快照保留几天，时段分析就能回看几天 |

- **全量 SQL 最长只能留 24 小时**：第一项上限是 86400。2026-10-21 在我方测试库上实测，设 604800（7 天）被拒（`invalid value`）。
  慢 SQL 那一项上限是 604800（7 天）
- **全量 SQL 记录量大**：我方测试库上 20 分钟约 146 万条。开到 24 小时前请评估 `statement_history` 所占存储。
  全量 SQL 记不记录还取决于 `track_stmt_stat_level` 的第一项（`OFF` 时不记），请一并确认
- 保留期调大都要占存储，**调多少由贵方 DBA 按存储余量定**。默认值下各功能都能用，只是能回看的时间短

查看当前值（任一会话执行；默认值以下面结果为准）：

```sql
SELECT name, setting, unit FROM pg_settings
 WHERE name IN ('track_stmt_retention_time', 'track_stmt_stat_level',
                'enable_asp', 'asp_sample_interval', 'asp_flush_rate', 'asp_retention_days',
                'enable_wdr_snapshot', 'wdr_snapshot_interval', 'wdr_snapshot_retention_days');
```

修改方式（`gs_guc` 或管理控制台）与是否需要重启，以贵方所用 GaussDB 版本的文档为准。

#### 路线二：离线压缩包（集群与跳板机都无外网时）

```
gaussdb-agent-v1.4.3-oc1.18.27-arm64.tar.gz     aarch64(鲲鹏)镜像(五个)
```

```bash
# 期望输出：... OK
```

**校验失败就停下**，不要继续 —— 传输损坏的镜像可能跑起来但行为异常。

### 1.2 载入镜像

```bash
# 按集群节点架构二选一(或都载)
docker load -i gaussdb-agent-v1.4.3-oc1.18.27-amd64.tar.gz

docker images | grep gaussdb-agent
```

**期望看到五个**（都由我方构建）：

```
gaussdb-agent-runtime      agent-v1.4.3-oc1.18.27-amd64
gaussdb-agent-kb-import    agent-v1.4.3-oc1.18.27-amd64
gaussdb-agent-gateway      agent-v1.4.3-oc1.18.27-amd64
gaussdb-agent-frontend     agent-v1.4.3-oc1.18.27-amd64
gaussdb-agent-kbstd        agent-v1.4.3-oc1.18.27-amd64
```

> **标签末尾那个 `-amd64` 是打包机器决定的**，两份包不对称：离线包在哪种架构的机器上
> 打的，那一份就没有后缀，另一份带后缀。**以包里的 `MANIFEST.txt` 为准** ——
> 它列的就是 `docker load` 之后的实际标签。下一步会先把后缀去掉。

### 1.3 去掉架构后缀，推内网仓库

```bash
REG=registry.内网/gaussdb-agent
TAG=agent-v1.4.3-oc1.18.27
SFX=-amd64          # MANIFEST.txt 里标签没有后缀时,这里写空:SFX=

for img in runtime kb-import gateway frontend kbstd; do
  docker tag gaussdb-agent-$img:$TAG$SFX gaussdb-agent-$img:$TAG
done
docker images | grep "gaussdb-agent.*$TAG$"
```

**必须是五行、且都不带后缀**再往下走 —— 后面的清单、`USER_IMAGE_TAG`、升级开关
用的都是不带后缀的标签，这一步漏了会在启动 Pod 时才以 `ImagePullBackOff` 出现。

```bash
for img in runtime kb-import gateway frontend kbstd; do
  docker tag gaussdb-agent-$img:$TAG $REG/gaussdb-agent-$img:$TAG
  docker push $REG/gaussdb-agent-$img:$TAG
done
```

### 1.4 解开清单并改镜像地址

```bash
tar xzf gaussdb-agent-v1.4.3-oc1.18.27-k8s.tar.gz && cd gaussdb-agent-k8s

# 把所有 image: 字段指向内网仓库
grep -rl "image: gaussdb-agent-" k8s/ \
  | xargs sed -i "s#image: gaussdb-agent-#image: $REG/gaussdb-agent-#"
# 用户容器的镜像名是网关按 gateway-config 拼出来的(模板里是 ${IMAGE}),上面的 sed 改不到,单独填前缀
sed -i "s#USER_IMAGE_REGISTRY: \"\"#USER_IMAGE_REGISTRY: \"$REG\"#" k8s/base/configmap-gateway.yaml

# 核对改对了
grep -rn "image:\|USER_IMAGE_REGISTRY:" k8s/ | grep -v "^.*#"
```

**逐行看一遍**，确认没有残留的公网地址 —— 内网集群拉不到会卡在 `ImagePullBackOff`。

### 1.5 如果集群无法访问镜像仓库

节点上直接 `docker load`，并把清单里的 `imagePullPolicy` 全改成 `IfNotPresent`
（默认已经是）。**每个可能调度到的节点都要载**。

> ⚠️ **只靠节点本地 `docker load` 有一个会在几周后才暴露的风险。**
>
> kubelet 会定期回收**无引用**的镜像。采用 `REAP_MODE: scale` 时，一段时间没人使用，
> 全部用户 Pod 会缩到 0 副本，此时用户镜像变成无引用 —— kubelet 可能把它清掉。
>
> - 集群能访问镜像仓库时：下次冷启动重新拉取即可，只是慢一点；
> - **纯离线、镜像只存在于节点本地时：清掉就再也回不来**，用户卡在 `ImagePullBackOff`，
>   而此时已经没有安装介质在手边。
>
> **因此离线环境也务必把镜像推进内网镜像仓库**（哪怕是一个最小的 registry），
> 不要只依赖节点本地。确实无法部署仓库时，请调高 kubelet 的镜像回收阈值
> （`--image-gc-high-threshold` / `--image-gc-low-threshold`）并纳入巡检。

## 阶段 2：命名空间与基础资源

### 2.1 准备 NAS 目录

由存储管理员在 NFS 导出根下建好，**属主 uid 1000**：

```bash
mkdir -p /export/gaussdb-agent/{users,admins,kb}
chown -R 1000:1000 /export/gaussdb-agent
chmod -R 775 /export/gaussdb-agent
```

### 2.2 接上 NAS：申请与供给两边

K8s 的存储分两边：`nas-pvc.yaml` 是**申请**（「要一个 500Gi 的 RWX 卷」），
**NFS 地址不在它里面**；真正说明「这个卷是哪台 NFS 的哪个目录」的是 PV 或 StorageClass，
那一边按贵方集群现状二选一：

**情形 ①：集群已有 RWX 的 StorageClass**（装了 NFS provisioner）

只改类名，不需要 PV：

```bash
sed -i "s/storageClassName: nas$/storageClassName: <贵方的类名>/" k8s/base/nas-pvc.yaml
```

**情形 ②：没有**

用我方给的静态 PV 样例填 NFS 地址，**先 apply 它**再 apply base：

```bash
cp k8s/base/nas-pv-nfs.example.yaml k8s/base/nas-pv-nfs.yaml
vi k8s/base/nas-pv-nfs.yaml          # 只填最后两行 server / path
kubectl apply -f k8s/base/nas-pv-nfs.yaml
```

样例里已经带好 `mountOptions: [nfsvers=4.1, hard, local_lock=all]`，
`persistentVolumeReclaimPolicy: Retain`。**两者都不要改**：`local_lock=all` 是容器做目录独占用的，
`Retain` 是因为那个卷里装的是用户的会话与知识库。

> 样例刻意不在 `kustomization.yaml` 里 —— 情形 ① 的客户多 apply 一个闲置 PV，
> 会把 PVC 绑到错的地方去。

### 2.3 应用

```bash
kubectl apply -k k8s/base
```

### 2.4 验证

```bash
kubectl -n gaussdb-agent get all,pvc,networkpolicy
```

**期望**：

- PVC `nas` 状态 `Bound`
- 五个 NetworkPolicy：`runtime-policy`、`kb-import-policy`、`gateway-policy`、`frontend-policy`、`kbstd-policy`（固定池化的两条随池子清单渲染）
- Deployment `gateway`（会 CrashLoop —— **正常**，Secret 还没建，见阶段 3）
- Deployment `frontend`（大盘前端，不依赖 Secret，应直接 Ready；卡在 `ImagePullBackOff` 就是 §1.3 漏推了它）
- Job `kbstd-install-v1-4-3` 的 Pod 为 `Completed`：GaussDB 官方文档集已装进知识库（§5.3）

**PVC 卡在 `Pending`**：`kubectl describe pvc nas`，看 Events。多半是 StorageClass 名字不对或 NFS 不可达。
**`kubectl get pv nas-nfs` 显示 `Released`**：之前删过命名空间，存储卷还记着旧申请。按顺序执行（数据不受影响）：`kubectl -n gaussdb-agent delete deploy,svc -l app=gaussdb-agent` → `kubectl -n gaussdb-agent delete pvc nas` → `kubectl patch pv nas-nfs --type json -p '[{"op":"remove","path":"/spec/claimRef"}]'` → `kubectl apply -f k8s/base/nas-pvc.yaml`。只做解除那一步不够：失败过的 PVC 会越来越晚才重试。

## 阶段 3：三个 Secret

**三个都不进版本库。** 样例文件 `k8s/base/*.example.yaml` 只是结构参考。

### 3.1 模型服务密钥

```bash
kubectl -n gaussdb-agent create secret generic model-api \
  --from-literal=MODEL_API_KEY='<模型服务密钥>'
```

### 3.2 网关信任凭据

```bash
TRUST=$(openssl rand -hex 24)
ADMIN=$(openssl rand -hex 24)

kubectl -n gaussdb-agent create secret generic gateway-auth \
  --from-literal=TRUST_SECRET="$TRUST" \
  --from-literal=ADMIN_TOKEN="$ADMIN"

echo "TRUST_SECRET(交给 SSO 团队): $TRUST"
echo "ADMIN_TOKEN(运维自用):      $ADMIN"
```

**`TRUST_SECRET` 要交给贵方 SSO 团队**，阶段 8 用。请走贵方的密钥传递流程，不要用即时通讯工具明文发送。

`ADMIN_TOKEN` 只在贵方要用控制 API 时才需要；不用就留空（则该组接口整体返回 404）。

### 3.3 SM2 私钥（中间件开了签名校验才需要）

```bash
kubectl -n gaussdb-agent create secret generic grmp-sm2 \
  --from-file=GRMP_SM2_PRIVATE_KEY=<客户签发的私钥文件>
```

**过渡期（密钥未批下来）跳过这一步**，阶段 4 把 `GRMP_SIGN_MODE` 设为 `headers-only`。

### 3.4 验证

```bash
kubectl -n gaussdb-agent get secret
# 期望:model-api / gateway-auth [/ grmp-sm2]
```

**不要 `kubectl get secret -o yaml` 打印内容**，那会把密钥写进终端历史与日志。

## 阶段 4：两个 ConfigMap

### 4.1 `agent-config`（用户 Pod 用）

```bash
kubectl -n gaussdb-agent edit configmap agent-config
```

```yaml
data:
  # --- 中间件 ---
  GRMP_API_HOST: "grmp.内网域名"
  GRMP_API_PORT: "8080"
  GRMP_PATH_PREFIX: "<中间件接口路径前缀>"   # 必填,中间件团队给,形如 /xxx/grmp/diagnostic/agent

  # 过渡期(密钥未批):只加 Appkey 与 Timestamp,不加 Signature
  GRMP_APPKEY: "<中间件给的 Appkey>"
  GRMP_SIGN_MODE: "headers-only"      # 密钥到位后改回 full,并建 Secret grmp-sm2
  GRMP_SIGN_TIMESTAMP: "s"            # 秒级,形如 1758431954

  # 把调用人工号发给中间件(字段名以中间件口径为准;两个都留空 = 不发)
  GRMP_USER_ID_HEADER: "X-User-Id"
  GRMP_USER_ID_PARAM: ""

  # --- 模型服务 ---
  MODEL_BASE_URL: "http://llm.内网域名/v1"
  MODEL_ID: "qwen3-32b"
  MODEL_PROVIDER_NAME: "model-service"

  # --- 网页剪藏(可选,知识库导入):允许剪藏的内网网站,空 = 关闭 ---
  KB_CLIP_ORIGINS: "https://wiki.内网域名,https://confluence.内网域名"
```

网页剪藏让知识库管理员把**需要登录**的内网网页（Wiki / Confluence / 门户）导入知识库：管理员在已登录的浏览器里点书签，
页面内容只经管理员的浏览器进来，导入容器**不访问**任何内网网站，阶段 7 的出网策略不用为它改。参数见《参数手册》「网页剪藏」。

### 4.2 `gateway-config`（网关用）

```bash

```

```yaml

  USER_IMAGE_REGISTRY: "registry.内网/gaussdb-agent"   # 用户容器镜像的仓库前缀,与 §1.3 的 $REG 相同
  PULL_POLICY: "IfNotPresent"
```

## 阶段 5：配置知识库

知识库**没有要初始化的数据库**：向量 + 词法索引是 NAS 上知识库目录里的一个文件 `kb/index/store.sqlite`
（SQLite + sqlite-vec，已装在 runtime 与 kb-import 两个镜像里）。只有导入容器 kb-import 的 `kb.py index` 写它
（持知识库写锁，在临时副本上写完原子替换）；runtime 与固定池化的槽位只读打开，所以 `/nas/kb` 只读挂载照常能查。

### 5.1 配置 kb.yaml

编辑 NAS 上的 `kb/kb.yaml`（全体共用一份，属主 uid 1000）：

```yaml
embeddings: {source: url, base_url: http://<embedding 端点>/v1, model: bge-m3, dims: 1024}
```

**没有 embedding 端点时**，整个文件写成一行即可，功能照常，只是没有语义检索：

```yaml
embeddings: {source: none}
```

> 不要再写 `store.pg`：那是旧版本连向量库用的，2026-10-23 起不用了。留着不报错，`kb.py index` / `kb.py health` 会提示可以删。

### 5.2 索引

**新部署不用手工做**：知识库管理员第一次导入材料时，导入流程会跑 `kb.py index` 建出 `kb/index/store.sqlite`。
在那之前检索走文件模式（状态行「模式:文件(…)」），不报错、不中断。

要手工建或重建（改了 embedding 配置、升级、排障）时，在导入容器里执行（管理员进过导入容器、容器在运行即可）：

```bash
kubectl -n gaussdb-agent exec deploy/kb-import-<管理员工号> -- sh -c \
  '. /data/env.sh && python3 /opt/agent/config/opencode/skills/gaussdb-kb-import/scripts/kb.py index'
```

**期望**：退出码 0；配了 embedding 时输出里有 `向量      : 引擎 sqlite-vec · … 覆盖 N/N`。
后配的 embedding 加 `--fill-missing` 补向量；换了嵌入模型或改了 `dims` 加 `--rebuild`。
退出码 2 = 有待处理项（向量覆盖不满、索引没写进去等），按输出处理；索引没写进去时原来那份不动，还没有索引就走文件模式。

### 5.3 官方文档集（部署时自动装上）

GaussDB 官方文档集（G25132C：GaussDB 25.1.32 集中式，6023 条，含检索索引）是**标准知识库**，随版本发布在第五个镜像
`gaussdb-agent-kbstd` 里。§2.3 的 `kubectl apply -k` 同时建了一次性 Job `kbstd-install-v1-4-3`，它把包装进 NAS 的 `kb/docsets/`：

- 装之前逐个文件核对 sha256，对不上就不换，原有的不动；同版本跳过，重复 apply 无害；
- 只动 `kb/docsets/<代号>/`，贵方自己的规范、案例、条目一个字节都不碰；换版时旧的留一份在 `kb/docsets/.rollback/`；
- 不需要知识库管理员登录、不经过模型、不要任何网络（`kbstd-policy` 出入站全拒）。

```bash
kubectl -n gaussdb-agent get job,pod -l app=gaussdb-kbstd
kubectl -n gaussdb-agent logs job/kbstd-install-v1-4-3
```

**期望**：Job `COMPLETIONS 1/1`，日志里是
`[installed] G25132C 已装上:云数据库 GaussDB 25.1.32 集中式版产品文档(for 华为云Stack 8.5.1) 01 · 6023 条 · …` 与
`分层 : L0 / L1 已按装好的文档集重建`（再 apply 一次是 `[skipped] … 已是这个版本`）。

- **`ImagePullBackOff`**：§1.3 漏推了 `gaussdb-agent-kbstd`，或 §1.4 的地址没改到 `kbstd-install.yaml`。
- **日志里是权限错误、Job 最终 `Failed`**：NAS 的 `kb/` 不是 uid 1000 可写（§2.1）。改好后
  `kubectl -n gaussdb-agent delete job kbstd-install-v1-4-3 && kubectl apply -f k8s/base/kbstd-install.yaml` 重跑一次。
- **「知识库正被 … 写入」**：管理员正在导入，Job 会自动重试。
- Job 完成 7 天后自动删掉；之后再 `apply -k` 会重跑一遍，同版本跳过。

装好后对话里问一个参数的默认值（如「idle_in_transaction_timeout 默认是多少」），回答里能引用 `PD-G25132C-…`，按产品文档上青色。
配了 embedding 而模型不是 bge-m3 时，这套文档先只走关键词检索，`kb.py index` 会按本库模型重算向量（`kb.py health` 有提示）。

## 阶段 7：网络策略收紧

默认清单里的地址段是**占位值**，必须按实际改，否则要么不通、要么过宽。

```bash
kubectl -n gaussdb-agent edit networkpolicy runtime-policy
```

需要按实际填的四处：

| 策略 | 出站目标 | 占位值 | 填什么 |
|---|---|---|---|
| `runtime-policy` | GRMP 中间件 | `10.0.0.0/8:8080` | 中间件实际地址段与端口 |
| `runtime-policy` | 模型服务 | `10.0.0.0/8:443,80` | 模型服务实际地址段 |
| `runtime-policy` / `kb-import-policy` | embedding 端点 | 同模型服务 | 若不同需另加 |
| `gateway-policy` | K8s apiserver | `10.96.0.0/12:443` | **按集群实际 Service CIDR** |

> **模型服务在公网时**（例如直接用公网的模型 API）：NetworkPolicy 只能按 IP 放行、不能按域名，
> 公网服务的 IP 又会变，只能把模型服务那条放宽到 `0.0.0.0/0` 的 443 —— 代价是用户容器能访问任意 HTTPS 地址。
> 测试环境可以接受；生产建议用内网模型服务，或经出网代理。
> **公司出网要经代理时**（集群里直连公网报 TLS 握手失败，而电脑上的浏览器能打开）：
> `bash k8s/tools/runtime-doctor.sh <工号> --fix --proxy <代理IP:端口>` 给用户容器配上 `HTTPS_PROXY`，
> 并把模型服务那条出网规则改成只放行代理的 IP 与端口（比放开 `0.0.0.0/0` 窄）。
> **漏改这一条的表现**：对话页报 `Cannot connect to API: Unable to connect`，而 key、地址、模型名都对。
> 改完用 `bash k8s/tools/runtime-doctor.sh <工号>` 从集群里实测一遍（附录 A）。

> **apiserver 那条最容易错。** 不同发行版的 Service CIDR 差别很大，而且
> NetworkPolicy 是按**真实端点**判的，不是按 Service ClusterIP。
> 查法：`kubectl -n default get endpoints kubernetes`。
> 填错的表现是网关日志里 `连不上 k8s API ... Connection refused`。

`gateway-policy` 的**入站**也要收紧成贵方 SSO / Ingress 的实际来源。
能打到网关就意味着能尝试伪造工号头（还挡在 `TRUST_SECRET` 那一层，但少一层暴露更好）。

`frontend-policy`（大盘前端）**不用改**：入站只收网关，出站一条都不放。它没有任何理由出网。

`kb-import-policy` 的入站多了一个 4095（网页剪藏接收），只从网关放行，**不用改**；网关出站到 4095 也已在清单里。

### 7.1 验证策略确实在生效

```bash
# 从 runtime Pod 里访问一个没放行的地址,应该不通
kubectl -n gaussdb-agent exec deploy/runtime-<某工号> -- \
  sh -c 'timeout 5 curl -s -o /dev/null -w "%{http_code}" http://example.com; echo'
# 期望:000(超时/被挡),而不是任何 HTTP 状态码
```

**返回了 HTTP 状态码** → NetworkPolicy 没生效，多半是 CNI 不支持。
**这是一个必须在上线前解决的问题**，否则 Pod 隔离只剩 subPath 一层。

## 阶段 8：对接 SSO

### 8.1 交给 SSO 团队的三样东西

1. **网关地址**：`gateway.gaussdb-agent.svc`（集群内）或贵方 Ingress 暴露的地址
2. **`TRUST_SECRET`**：阶段 3.2 生成的那串
3. **下面这段配置要求**

### 8.2 给 SSO 团队的配置要求（可直接转发）

> 请在已完成认证的转发位置上，加入以下配置。
>
> **必须注入的请求头**
>
> | 头 | 内容 |
> |---|---|
> | `X-Agent-User` | 用户工号。小写字母数字与 `-`，最长 54 字符 |
> | `X-Agent-Roles` | 用户所属角色/组，逗号分隔（可选） |
> | `X-Agent-Trust` | 我方提供的共享密钥，原样透传 |
>
> **必须的代理设置**（nginx 示例；其它产品请找等价项）
>
> ```nginx
> location /gaussdb-agent/ {
>     proxy_set_header X-Agent-User   $remote_user;
>     proxy_set_header X-Agent-Roles  $user_groups;
>     proxy_set_header X-Agent-Trust  "<共享密钥>";
>     proxy_pass http://gateway.gaussdb-agent.svc/;
>
>     proxy_buffering    off;    # ← 必需
>     proxy_cache        off;    # ← 必需
>     proxy_http_version 1.1;    # ← 必需
>     proxy_read_timeout 1h;     # ← 必需
>     gzip               off;
> }
> ```
>
> **为什么这四行是必需的**：本系统用 SSE（`text/event-stream`）向浏览器推送模型输出，
> 每 10 秒一次心跳。任何一层缓冲响应体，页面就会一直转圈、消息迟迟不出来 ——
> 表现不像「断开」，像「卡住」，最难排查。
>
> **请一并确认两条硬限制**
>
> 1. 是否存在「单个连接最长 N 分钟」的限制？SSE 是永不结束的连接。
> 2. 闲置回收（若有）是按**字节活动**还是按**新请求数**判定？
>    本系统开着页面发呆时有心跳但没有新请求，按请求数判会误杀。

### 8.3 SSO 未就绪时如何继续

不必等。用 `curl` 模拟 SSO 的效果，先把阶段 9 做完：

```bash
curl -H "X-Agent-Trust: $TRUST" -H "X-Agent-User: u0001" http://127.0.0.1:18080/...
```

要在**浏览器**里看大盘和对话页，按 [`现场测试-模拟SSO.md`](./现场测试-模拟SSO.md) 起一个本机的模拟 SSO
（`k8s/tools/sso-sim.py`，约 5 分钟，不改集群配置，只用于测试）。

## 阶段 9：开通第一个用户并端到端验收

### 9.1 开通一个用户

开通 = **创建他本人的 GRMP 令牌 Secret**。其余（Pod、口令、NAS 目录）网关自动完成。

```bash
kubectl -n gaussdb-agent create secret generic grmp-token-u0001 \
  --from-literal=GRMP_AUTH_TOKEN='<该用户的中间件令牌>'
```

知识库管理员另需在角色里带上 `kb-admin`（由 `X-Agent-Roles` 头传入），
或写进 ConfigMap `agent-roles`。

> **为什么网关不自动建这个 Secret**：令牌由贵方中间件按人签发，网关无从得知。
> 缺它时用户会看到 503「您的环境尚未开通」，网关日志里写明缺的是哪个 Secret。

### 9.2 验收清单

逐条执行，**全绿才算上线**：

```bash
TRUST=<共享密钥>; GW=http://127.0.0.1:18080
H=(-H "X-Agent-Trust: $TRUST" -H "X-Agent-User: u0001")
```

| # | 验什么 | 命令 | 期望 |
|---|---|---|---|
| 1 | 首次访问自动建 Pod | `time curl -s -m 150 -o /dev/null -w "%{http_code}\n" "${H[@]}" $GW/global/health` | `200`，30 秒内 |
| 2 | Pod 真的建了 | `kubectl -n gaussdb-agent get deploy runtime-u0001` | `READY 1/1` |
| 3 | 能对话 | 见下方 9.3 | 模型正常回复 |
| 4 | 能连数据库 | 对话里说「登录 `<实例IP>` 的 `<库名>`」 | 返回已登录与主备状态 |
| 5 | 诊断技能可用 | 对话里说「看下当前有没有慢 SQL」 | 返回报告 |
| 6 | 知识库可查 | 对话里说「知识库里有没有 CPU 相关的案例」 | 返回案例或「无」 |
| 7 | **导入被正确拒绝**（普通用户） | 对话里说「帮我导入一份工单」 | 答「本环境不含导入功能」 |
| 8 | 未开通用户被挡 | 换 `X-Agent-User: u9999` 重复第 1 条 | `503`，日志写明缺哪个 Secret |
| 9 | 无信任凭据被挡 | 去掉 `X-Agent-Trust` 重复第 1 条 | `403` |
| 10 | 跨用户不可见 | 在 u0001 的 Pod 里 `ls /nas` | 只有 `me` 和 `kb` |
| 11 | 回收生效 | 见 9.4 | 副本数归 0 |
| 12 | 重连恢复 | 回收后重复第 1 条 | `200`，会话还在 |
| 13 | 大盘经网关可达、且只看本人 | `curl -s -o /dev/null -w "%{http_code}\n" "${H[@]}" $GW/dash/health` 与 `curl -s "${H[@]}" $GW/reports/whoami.json` | `200`；`{"user_id": "u0001"}` |
| 14 | 官方文档集已自动装上 | `kubectl -n gaussdb-agent logs job/kbstd-install-v1-4-3` | `[installed]` 或 `[skipped]` 一行，6023 条（§5.3） |

第 13 条在浏览器里看：接好 SSO 后打开 `/dash/health`。第 5 条跑过一次健康检查后，健康检查大盘上就有那份报告；
**大盘只展示本人跑过的报告**，没跑过的技能对应的大盘是空的，这不是故障。

### 9.3 第 3 条的具体做法

```bash
S=$(curl -s "${H[@]}" -X POST "$GW/session?directory=/data/state/workspace" \
      -H 'content-type: application/json' -d '{}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])')

curl -s "${H[@]}" -X POST "$GW/session/$S/message?directory=/data/state/workspace" \
  -H 'content-type: application/json' -d '{"parts":[{"type":"text","text":"只回四个字:部署验收"}]}'
```

也可以直接用浏览器：`$GW/L2RhdGEvc3RhdGUvd29ya3NwYWNl`
（那串是容器内工作目录 `/data/state/workspace` 的 base64url，是 opencode 的项目路由）。

> **不要落在 `/`**：那一页的项目列表是浏览器本地记的，新浏览器为空，用户会以为系统坏了。

### 9.4 第 11 条的具体做法

```bash
# 把活动时间改成很久以前,等回收器扫描(默认 120 秒一轮)
kubectl -n gaussdb-agent annotate deploy runtime-u0001 \
```

## 附录 A：常见问题定位

**用户容器相关的问题，先跑一键诊断**（只读，约 30 秒到 1 分钟；离线包里在 `k8s/tools/`）：

```bash
bash k8s/tools/runtime-doctor.sh <工号>                          # 只诊断,不改任何配置
bash k8s/tools/runtime-doctor.sh <工号> --fix                    # 修复能自动修的项,再复查一遍
bash k8s/tools/runtime-doctor.sh <工号> --fix --grmp <中间件IP:端口>   # 顺带把中间件地址改对
bash k8s/tools/runtime-doctor.sh <工号> --fix --proxy <代理IP:端口>   # 用户容器经公司代理访问模型服务
bash k8s/tools/runtime-doctor.sh <工号> --login                  # 再经网关真登录一次,看会不会被反复收掉(约 3 分钟)
```

工号只写一个（`bash` 是运行脚本的命令，不是参数）。它查配置与开通、个人目录能不能写、用户容器的重启原因、
出网策略、运行脚本这台电脑的代理设置，并从集群里**实际连一次**模型与中间件
（受出网策略约束与不受约束的两个临时 Pod 对照，按 TCP 连没连上分清是策略挡的、集群本身出不去，还是 TLS / 代理的问题）。
最后的「诊断意见」每个问题一条：原因判断，以及可以直接复制执行的命令（有的话）。
`--fix` 能修：模型服务出网被挡（放宽规则，或给了 `--proxy` 时改成经代理）、个人目录缺失或写不进、
中间件地址（需给 `--grmp`）。改了什么逐条打印，改完自动复查。
需要 bash 与 kubectl，Windows 用 Git Bash 即可。修不好时把整段输出发给我方。

| 现象 | 先看 | 常见原因 |
|---|---|---|
| 对话页报 `Cannot connect to API: Unable to connect` | `runtime-doctor.sh <工号>` | 模型服务的出网规则还是占位网段（§7），模型在公网时尤其容易漏 |
| 诊断结果「TCP 连上了，TLS 握手失败」 | 诊断意见里的命令 | 公司出口不允许直连外网，要经公司代理：`--fix --proxy <代理IP:端口>`（§7） |
| 已配代理，诊断结果「集群连不上代理」 | 诊断意见 | 请求根本没到代理：代理 IP / 端口不对，或集群节点访问不到它（只对办公网开放、要经 VPN），或代理 IP 和集群 / Docker 网络的网段重叠（172.17–172.31 常见）。**不要**再执行一遍 `--proxy` |
| 用户容器起不来，状态 `Init:Error` 或日志 `mkdir: ... Permission denied` | `runtime-doctor.sh <工号>` | 个人目录写不进：上一层 `users/` 不是 uid 1000 可写，或 `users/<工号>` 是旧版本（v1.2.0 之前首次登录时 kubelet 以 root 建出）留下的。`--fix` 可修该工号；根治是把 `users/` 改成属主 1000:1000、权限 775（§2.1） |
| 登录数据库连不上中间件 | `runtime-doctor.sh <工号>` | `agent-config` 的 `GRMP_API_HOST` 还是 `localhost` / 样例值，或中间件出网规则没按实际填 |
| 网关 CrashLoop | `logs -l app=agent-gateway` | 配置不全（刻意拒绝启动），按报错改 |
| 网关 `连不上 k8s API` | `gateway-policy` 的出站 | apiserver 地址段没按实际填（§7） |
| 用户 503 | 网关日志 | 缺 `grmp-token-<工号>` |
| 用户容器反复被缩成 0、登录一直没响应 | `runtime-doctor.sh <工号> --login` | 看结论：A 网关没刷新活动时间 / B 刷新了仍被回收（这两种发给我方）/ C 没被回收但容器没就绪（脚本自动打印状态、日志与事件）/ D 正常 —— 多半是有人绕过网关手工拉起过容器（`kubectl scale` / `rollout restart` 不刷新活动时间） |
| 用户看到 503「环境启动失败（…）」或 504 | 网关日志里该工号那一行（`logs -l app=agent-gateway --prefix`），再 `describe pod -l user=<工号>` | 括号里就是原因类别：拉不到镜像 / 容器配置缺失 / 个人目录初始化失败 / NAS 挂不上 / 调度不上。前三类网关不等满超时，当场返回 503 |
| 用户容器一直 `Pending`，Events 写 `unbound immediate PersistentVolumeClaims` | `get pv nas-nfs` | PV 是 `Released`：删过命名空间后没解除旧绑定，见 §2.4 |
| 用户 403 | SSO 侧 | `X-Agent-Trust` 没注入或值不对 |
| 页面一直转圈 | SSO 侧代理 | 没关缓冲（§8.2） |
| 页面「已中断」 | 用户操作 | 空输入框按回车 = 中断。刷新重发即可 |
| Pod 起不来，日志停在 `独占标记` | NAS | `.owner` 被上一个 Pod 占着；等 90 秒过期或人工删 |
| 对话历史丢了一段 | Pod 日志搜「非优雅」 | 上次是 OOMKill/驱逐，NAS 上有 `.unclean-*` 快照 |
| 知识库查不到应该有的案例 | `kb.py health` 看状态行 | 「模式:文件」= 还没建索引（§5.2）；「向量:未启用」= 没配 embedding 或 sqlite-vec 加载不了，只有关键词检索 |
| 导入后提示「写索引失败 … 已回退到文件模式」 | 导入容器里 `ls -ld /nas/kb/index`、`df -h /nas/kb` | `kb/index/` 不是 uid 1000 可写，或 NAS 满了；修好后重跑 `kb.py index`（§5.2） |
| 大盘 502「大盘服务未部署或不可达」 | `get deploy frontend` | 前端没起来（§6.4），或 `FRONTEND_SERVICE` 与 Service 名不一致。**不影响对话与报告** |
| 大盘打开是空的 / 「还没有报告」 | 本人是否跑过该技能 | 大盘只展示**本人跑过的**报告，不会替用户采集。在会话里跑一次对应技能即有 |
| 大盘上某块空白、其余正常 | 前端与用户镜像版本 | 两边版本错开（§10.5），报告里没有页面要的字段。一起升到同一版本 |

## 附录 C：镜像拉取令牌的管理

采用「从镜像仓库拉取」路线时，我方会提供一个**只读令牌**（`read:packages`）。
它是一个需要有人负责的凭据，请纳入贵方的密钥管理流程。

| 项 | 说明 |
|---|---|
| 谁的令牌 | **贵方自己账号的令牌**，由贵方实施人员自行生成，我方不经手 |
| 能做什么 | 只能拉取本项目的四个容器镜像（权限 `read:packages`） |
| 源码呢 | 源码仓库是公开的，**不需要令牌** |
| 用途 | 只在**首次部署**与**升级取新镜像**时使用；拉完推进内网仓库后，集群不再需要它 |
| 存放 | **不要**写进 K8s 清单、部署脚本或 CI 配置。建议放贵方密钥管理系统，取用时临时注入 |
| 轮换 | 人员变动、到期、或怀疑泄露时请联系我方重签。轮换不影响已拉到内网仓库的镜像 |
| 失效影响 | 只影响「再次从外网取新版本」，**不影响已部署环境的运行** |
| 泄露处置 | 立即联系我方作废并重签。已部署环境不受影响，但请同步排查是否有非预期的仓库访问 |

**集群本身不需要这个令牌。** 正确做法是：跳板机用它拉取 → 推进贵方内网仓库 →
清单里的 `image:` 指向内网仓库。集群只认内网仓库，与外网彻底解耦。

若清单里直接写 `ghcr.io/...` 地址，集群每次拉镜像都要出外网并持有令牌，
这既不符合多数行内网络策略，也会让令牌轮换变成一次全集群改动 —— **不建议**。
