# 部署手册：从零到上线

> 面向：负责实施的运维工程师。
> 用法：**从头到尾照做**。每一步都给了「怎么验证成功」与「失败了看哪里」。
> 全程约 3–5 小时（不含网络申请、密钥审批、SSO 侧改动的等待时间）。
>
> 架构与设计说明见 [`接入手册-SSO与K8s.md`](./接入手册-SSO与K8s.md)。本篇只讲**怎么做**。

## 阶段 0：开工前的清单

### 0.1 需要提前拿到的东西

逐项确认，**缺任何一项都会在中途卡住**：

- [ ] **K8s 集群**访问权限，能在目标命名空间建 Deployment / Service / Secret / ConfigMap / NetworkPolicy / StatefulSet / ServiceAccount / Role / RoleBinding
- [ ] **CNI 支持 NetworkPolicy**（Calico / Cilium 等）。不确定就问集群管理员，**不要假设**
- [ ] **RWX 存储**（NFS v4.1），容量按 `人数 × 3 GB + 知识库 20 GB` 估
- [ ] **内网镜像仓库**地址与推送权限
- [ ] **模型服务**：地址（OpenAI 兼容，含 `/v1`）、密钥、模型 id
- [ ] **embedding 端点**：地址、模型名、维度 —— 见 §0.3，**这一项最容易被漏**
- [ ] **GRMP 中间件**：地址、端口；以及**按人签发令牌的获取方式**
- [ ] **SSO 侧**：能在转发时注入请求头的位置（网关 / WAF / Ingress）
- [ ] 一台能执行 `kubectl` 与 `docker` 的跳板机

### 0.2 命名约定

本手册全程使用：

| 项 | 值 | 改了要一起改的地方 |
|---|---|---|
| 命名空间 | `gaussdb-agent` | 所有清单 + `GATEWAY_NAMESPACE` |
| 镜像仓库 | `registry.内网/gaussdb-agent` | 所有清单的 `image:` 字段 |
| 版本标签 | `agent-v1.0.4-oc1.18.27` | `gateway-config.USER_IMAGE_TAG` + 网关自身的 `image:` |

### 0.3 embedding 端点：现在就去确认

**这是唯一一项「前置时间可能以周计」的依赖**，其余都能当天解决。

> 请贵方模型服务团队回答：**是否提供 OpenAI 兼容的 `/v1/embeddings` 接口？**

embedding 模型与对话模型是两种模型。模型服务跑的是 Qwen 之类的对话模型时，
`/v1/embeddings` 往往直接 404（vLLM 装一个对话模型就是这样）。

- **有** → 记下模型名与维度，阶段 5 用
- **没有** → 需要另外部署一个（Xinference / Ollama 等，装 `bge-m3` 之类），**现在就去申请**
- **暂时没有也能上线** → 知识库退到纯文件模式，功能可用但语义检索弱；后补即可，不阻塞

## 阶段 1：取交付物、载入镜像、推内网仓库

### 1.1 取交付物：两条路，按贵方网络条件二选一

#### 路线一：从镜像仓库拉取（集群或跳板机能访问外网时）

镜像发布在 GitHub Container Registry（GHCR），**镜像与源码仓库均为私有**，
需先用我方提供的访问令牌登录。以下命令已实测通过：

```bash
# 1) 登录 GHCR。令牌由我方单独提供,请走贵方密钥流程接收,不要用即时通讯工具传递。
echo '<访问令牌>' | docker login ghcr.io -u <我方提供的账号> --password-stdin

# 2) 拉取三个镜像
TAG=agent-v1.0.4-oc1.18.27
for img in runtime kb-import gateway; do
  docker pull ghcr.io/sqlrush/gaussdb-agent-$img:$TAG
done

# 3) 向量库基础镜像来自公共仓库,不需要令牌
docker pull opengauss/opengauss:7.0.0-RC1

# 4) 核对拉到了四个
docker images | grep -E "gaussdb-agent|opengauss"
```

拉完**立刻推进贵方内网仓库**（§1.3），不要让集群直接依赖外网 —— 理由见附录 C。

**源码**也在同一个私有仓库，同一个令牌即可访问：

```bash
git clone https://<访问令牌>@github.com/sqlrush/gh_agent_k8s.git
# 或配好 SSH key 后:git clone git@github.com:sqlrush/gh_agent_k8s.git
```

> 源码同时随交付包提供（`*-k8s.tar.gz`），**不访问 GitHub 也能拿到完整源码**。

#### 路线二：离线压缩包（集群与跳板机都无外网时）



```
gaussdb-agent-v1.0.4-oc1.18.27-amd64.tar.gz     x86_64 镜像(四个)
gaussdb-agent-v1.0.4-oc1.18.27-arm64.tar.gz     aarch64(鲲鹏)镜像(四个)
gaussdb-agent-v1.0.4-oc1.18.27-k8s.tar.gz       K8s 清单 + 脚本 + 文档
<上述三个>.sha256                                校验和
```

两条路线到 §1.2 之后完全一致。

> 若贵方具备内网 git 与构建条件：`git clone <内网仓>/gh_agent_k8s && git checkout agent-v1.0.4`，
> 再 `bash scripts/build-images.sh agent-v1.0.4-oc1.18.27` 自行构建。
> 构建需要能拉取基础镜像；不具备外网条件时请直接使用离线包。

```bash
# 校验
sha256sum -c gaussdb-agent-v1.0.4-oc1.18.27-amd64.tar.gz.sha256
# 期望输出：... OK
```

**校验失败就停下**，不要继续 —— 传输损坏的镜像可能跑起来但行为异常。

### 1.2 载入镜像

```bash
# 按集群节点架构二选一(或都载)
docker load -i gaussdb-agent-v1.0.4-oc1.18.27-amd64.tar.gz

docker images | grep gaussdb-agent
```

**期望看到四个**（前三个由我方构建，第四个是向量库所用的 openGauss 基础镜像）：

```
gaussdb-agent-runtime      agent-v1.0.4-oc1.18.27
gaussdb-agent-kb-import    agent-v1.0.4-oc1.18.27
gaussdb-agent-gateway      agent-v1.0.4-oc1.18.27
opengauss/opengauss        7.0.0-RC1
```

### 1.3 推内网仓库

```bash
REG=registry.内网/gaussdb-agent
TAG=agent-v1.0.4-oc1.18.27

for img in runtime kb-import gateway; do
  docker tag gaussdb-agent-$img:$TAG $REG/gaussdb-agent-$img:$TAG
  docker push $REG/gaussdb-agent-$img:$TAG
done
docker tag opengauss/opengauss:7.0.0-RC1 $REG/opengauss:7.0.0-RC1
docker push $REG/opengauss:7.0.0-RC1
```

### 1.4 解开清单并改镜像地址

```bash
tar xzf gaussdb-agent-v1.0.4-oc1.18.27-k8s.tar.gz && cd gaussdb-agent-k8s

# 把所有 image: 字段指向内网仓库
grep -rl "image: gaussdb-agent-\|image: opengauss/" k8s/ \
  | xargs sed -i "s#image: gaussdb-agent-#image: $REG/gaussdb-agent-#; s#image: opengauss/#image: $REG/opengauss:#"

# 核对改对了
grep -rn "image:" k8s/ | grep -v "^.*#"
```

**逐行看一遍**，确认没有残留的公网地址 —— 内网集群拉不到会卡在 `ImagePullBackOff`。

### 1.5 如果集群无法访问镜像仓库

节点上直接 `docker load`，并把清单里的 `imagePullPolicy` 全改成 `IfNotPresent`
（默认已经是）。**每个可能调度到的节点都要载**。

> ⚠️ **只靠节点本地 `docker load` 有一个会在几周后才暴露的风险。**
>
> kubelet 会定期回收**无引用**的镜像。采用 `REAP_MODE: scale` 时，一段时间没人使用，
> 全部用户 Pod 会缩到 0 副本，此时用户镜像变成无引用 —— kubelet 可能把它清掉。
>
> - 集群能访问镜像仓库时：下次冷启动重新拉取即可，只是慢一点；
> - **纯离线、镜像只存在于节点本地时：清掉就再也回不来**，用户卡在 `ImagePullBackOff`，
>   而此时已经没有安装介质在手边。
>
> **因此离线环境也务必把镜像推进内网镜像仓库**（哪怕是一个最小的 registry），
> 不要只依赖节点本地。确实无法部署仓库时，请调高 kubelet 的镜像回收阈值
> （`--image-gc-high-threshold` / `--image-gc-low-threshold`）并纳入巡检。

## 阶段 2：命名空间与基础资源

### 2.1 准备 NAS 目录

由存储管理员在 NFS 导出根下建好，**属主 uid 1000**：

```bash
mkdir -p /export/gaussdb-agent/{users,admins,kb}
chown -R 1000:1000 /export/gaussdb-agent
chmod -R 775 /export/gaussdb-agent
```

### 2.2 改 PV / PVC 指向实际 NAS

编辑 `k8s/base/nas-pvc.yaml`：

```yaml
# PV 部分
nfs:
  server: <NFS 服务器地址>
  path: /export/gaussdb-agent
mountOptions: [nfsvers=4.1, hard, local_lock=all]
```

> `local_lock=all` 不能省。SQLite 在 NFS 上的锁行为依赖它。

### 2.3 应用

```bash
kubectl apply -k k8s/base
```

### 2.4 验证

```bash
kubectl -n gaussdb-agent get all,pvc,networkpolicy
```

**期望**：

- PVC `nas` 状态 `Bound`
- 三个 NetworkPolicy：`runtime-policy`、`kb-import-policy`、`gateway-policy`、`vectordb-policy`
- StatefulSet `vectordb`（可能还没 Ready，正常）
- Deployment `gateway`（会 CrashLoop —— **正常**，Secret 还没建，见阶段 3）

**PVC 卡在 `Pending`**：`kubectl describe pvc nas`，看 Events。多半是 StorageClass 名字不对或 NFS 不可达。

## 阶段 3：四个 Secret

**四个都不进版本库。** 样例文件 `k8s/base/*.example.yaml` 只是结构参考。

### 3.1 模型服务密钥

```bash
kubectl -n gaussdb-agent create secret generic model-api \
  --from-literal=MODEL_API_KEY='<模型服务密钥>'
```

### 3.2 网关信任凭据

```bash
TRUST=$(openssl rand -hex 24)
ADMIN=$(openssl rand -hex 24)

kubectl -n gaussdb-agent create secret generic gateway-auth \
  --from-literal=TRUST_SECRET="$TRUST" \
  --from-literal=ADMIN_TOKEN="$ADMIN"

echo "TRUST_SECRET(交给 SSO 团队): $TRUST"
echo "ADMIN_TOKEN(运维自用):      $ADMIN"
```

**`TRUST_SECRET` 要交给贵方 SSO 团队**，阶段 8 用。请走贵方的密钥传递流程，不要用即时通讯工具明文发送。

`ADMIN_TOKEN` 只在贵方要用控制 API 时才需要；不用就留空（则该组接口整体返回 404）。

### 3.3 向量库口令

**三个口令，故意分开**：超级用户初始化用、kb-import 读写用、runtime 只读用。

```bash
kubectl -n gaussdb-agent create secret generic vectordb-auth \
  --from-literal=GS_PASSWORD="$(openssl rand -base64 12 | tr -d '/+=')Aa1@" \
  --from-literal=KB_RW="$(openssl rand -base64 12 | tr -d '/+=')Rw1@" \
  --from-literal=KB_RO="$(openssl rand -base64 12 | tr -d '/+=')Ro1@"
```

> openGauss 的口令强度要求：长度 ≥ 8，且含大写 / 小写 / 数字 / 特殊字符中至少三类。
> 不满足时容器初始化失败，而**日志里只有一句 `Please check password`** —— 上面的写法已满足。

### 3.4 SM2 私钥（中间件开了签名校验才需要）

```bash
kubectl -n gaussdb-agent create secret generic grmp-sm2 \
  --from-file=GRMP_SM2_PRIVATE_KEY=<客户签发的私钥文件>
```

**过渡期（密钥未批下来）跳过这一步**，阶段 4 把 `GRMP_SIGN_MODE` 设为 `headers-only`。

### 3.5 验证

```bash
kubectl -n gaussdb-agent get secret
# 期望:model-api / gateway-auth / vectordb-auth [/ grmp-sm2]
```

**不要 `kubectl get secret -o yaml` 打印内容**，那会把密钥写进终端历史与日志。

## 阶段 4：两个 ConfigMap

### 4.1 `agent-config`（用户 Pod 用）

```bash
kubectl -n gaussdb-agent edit configmap agent-config
```

```yaml
data:
  # --- 中间件 ---
  GRMP_API_HOST: "grmp.内网域名"
  GRMP_API_PORT: "8080"

  # 过渡期(密钥未批):只加 Appkey 与 Timestamp,不加 Signature
  GRMP_APPKEY: "F-GAUSS-AGENT"
  GRMP_SIGN_MODE: "headers-only"      # 密钥到位后改回 full,并建 Secret grmp-sm2
  GRMP_SIGN_TIMESTAMP: "s"            # 秒级,形如 1758431954

  # 把调用人工号发给中间件(字段名以中间件口径为准;两个都留空 = 不发)
  GRMP_USER_ID_HEADER: "X-User-Id"
  GRMP_USER_ID_PARAM: ""

  # --- 模型服务 ---
  MODEL_BASE_URL: "http://llm.内网域名/v1"
  MODEL_ID: "qwen3-32b"
  MODEL_PROVIDER_NAME: "model-service"
```

### 4.2 `gateway-config`（网关用）

```bash
kubectl -n gaussdb-agent edit configmap gateway-config
```

```yaml
data:
  USER_IMAGE_TAG: "agent-v1.0.4-oc1.18.27"   # 升级开关,见下方注
  PULL_POLICY: "IfNotPresent"

  USER_HEADER: "X-Agent-User"                # 与 SSO 团队约定
  ROLES_HEADER: "X-Agent-Roles"
  KB_ADMIN_ROLES: "kb-admin"                 # 哪些角色值算知识库管理员

  REAP_MODE: "scale"                         # scale=缩到0副本 / delete=删Deployment
  IDLE_SECONDS: "1800"                       # 下限 300,低于此值网关拒绝启动

  TRUST_CIDRS: ""                            # 用共享密钥时可留空
```

> **`USER_IMAGE_TAG` 是升级开关**：改它 + 重启网关 = **之后登录**的人用新版本，
> 已经在用的人不受影响（他们的 Pod 不动）。
> 故意不给默认值 —— 默认成 `latest` 会让「升级」悄悄发生在某个人下次登录时。

## 阶段 5：向量库初始化

### 5.1 等 vectordb 就绪

```bash
kubectl -n gaussdb-agent rollout status statefulset/vectordb --timeout=600s
```

openGauss 首次初始化较慢（1–5 分钟），探针已按此设置。

**起不来**：`kubectl -n gaussdb-agent logs vectordb-0 | tail -30`。
最常见是 §3.3 的口令强度不满足。

### 5.2 建库、建用户、授权

```bash
bash scripts/k8s/init-vectordb.sh
```

脚本是幂等的，可重复执行。**期望输出**：

```
== 1 DataVec 自检
   ✓ vector 类型在,<=> 可用(样例距离 .006001)
== 3 建库、建用户、授权(幂等)
   kb 库已建
   用户 kb_rw 已建
   用户 kb_ro 已建
== 4 库内授权(schema 与未来新建的表)
   已授权(含 default privileges)
== 5 验一遍两个用户真能按预期连
   kb_rw 能建表:        1
   kb_ro 建表应被拒:    ERROR: permission denied for schema public
   kb_ro 能连能查:      1
```

**第 1 步失败**（没有 vector 类型）→ 镜像版本不对，必须 openGauss 7.0 以上。
**第 5 步 kb_ro 居然能建表** → 授权没生效，不要继续，重跑脚本并检查输出。

### 5.3 配置知识库

编辑 NAS 上的 `kb/kb.yaml`（全体共用一份）：

```yaml
store:
  pg: {host: vectordb, port: 5432, database: kb, user: kb_ro, credential: kb-pg,
       user_env: KB_PG_USER, password_env: KB_PG_PASSWORD}
embeddings: {source: url, base_url: http://<embedding 端点>/v1, model: bge-m3, dims: 1024}
```

**没有 embedding 端点时**，整个文件写成一行即可，功能照常，只是没有语义检索：

```yaml
embeddings: {source: none}
```

## 阶段 6：启动网关并自检

### 6.1 重启并等待

```bash
kubectl -n gaussdb-agent rollout restart deploy/gateway
kubectl -n gaussdb-agent rollout status deploy/gateway --timeout=180s
```

### 6.2 看启动日志

```bash
kubectl -n gaussdb-agent logs -l app=agent-gateway --tail=5
```

**期望一行**：

```
网关就绪:0.0.0.0:8080 · 命名空间 gaussdb-agent · 用户镜像标签 agent-v1.0.4-oc1.18.27
       · 回收 scale(闲置 1800 秒)· 信任来源 共享密钥 · 控制 API 已启用
```

**如果是 `配置错误,网关拒绝启动: ...`**：这是**刻意的** —— 网关不会带着不完整的配置跑起来。
按报错信息改配置即可。最常见：

| 报错 | 原因 |
|---|---|
| `GATEWAY_TRUST_SECRET 与 GATEWAY_TRUST_CIDRS 一个都没配` | 阶段 3.2 漏了，或 Secret 名字不对 |
| `缺 GATEWAY_IMAGE_TAG` | 阶段 4.2 的 `USER_IMAGE_TAG` 没填 |
| `GATEWAY_IDLE_SECONDS=60 太小` | 下限 300 秒 |

### 6.3 连通性自检

```bash
kubectl -n gaussdb-agent port-forward svc/gateway 18080:80 &

curl -s http://127.0.0.1:18080/healthz
# 期望:{"ok": true, "version": "gaussdb-agent-gateway"}

# 不带信任凭据 → 必须 403
curl -s -o /dev/null -w "%{http_code}\n" -H "X-Agent-User: u0001" http://127.0.0.1:18080/session
# 期望:403

# 控制 API(配了 ADMIN_TOKEN 时)
curl -s -H "X-Admin-Token: $ADMIN" http://127.0.0.1:18080/admin/pods
# 期望:{"pods": []}
```

**第二条返回 200 而不是 403** → 说明信任判定被绕过了，**立刻停下排查**。
常见原因：`TRUST_CIDRS` 配得太宽，把 port-forward 的来源（127.0.0.1）也算成可信。

## 阶段 7：网络策略收紧

默认清单里的地址段是**占位值**，必须按实际改，否则要么不通、要么过宽。

```bash
kubectl -n gaussdb-agent edit networkpolicy runtime-policy
```

需要按实际填的四处：

| 策略 | 出站目标 | 占位值 | 填什么 |
|---|---|---|---|
| `runtime-policy` | GRMP 中间件 | `10.0.0.0/8:8080` | 中间件实际地址段与端口 |
| `runtime-policy` | 模型服务 | `10.0.0.0/8:443,80` | 模型服务实际地址段 |
| `runtime-policy` / `kb-import-policy` | embedding 端点 | 同模型服务 | 若不同需另加 |
| `gateway-policy` | K8s apiserver | `10.96.0.0/12:443` | **按集群实际 Service CIDR** |

> **apiserver 那条最容易错。** 不同发行版的 Service CIDR 差别很大，而且
> NetworkPolicy 是按**真实端点**判的，不是按 Service ClusterIP。
> 查法：`kubectl -n default get endpoints kubernetes`。
> 填错的表现是网关日志里 `连不上 k8s API ... Connection refused`。

`gateway-policy` 的**入站**也要收紧成贵方 SSO / Ingress 的实际来源。
能打到网关就意味着能尝试伪造工号头（还挡在 `TRUST_SECRET` 那一层，但少一层暴露更好）。

### 7.1 验证策略确实在生效

```bash
# 从 runtime Pod 里访问一个没放行的地址,应该不通
kubectl -n gaussdb-agent exec deploy/runtime-<某工号> -- \
  sh -c 'timeout 5 curl -s -o /dev/null -w "%{http_code}" http://example.com; echo'
# 期望:000(超时/被挡),而不是任何 HTTP 状态码
```

**返回了 HTTP 状态码** → NetworkPolicy 没生效，多半是 CNI 不支持。
**这是一个必须在上线前解决的问题**，否则 Pod 隔离只剩 subPath 一层。

## 阶段 8：对接 SSO

### 8.1 交给 SSO 团队的三样东西

1. **网关地址**：`gateway.gaussdb-agent.svc`（集群内）或贵方 Ingress 暴露的地址
2. **`TRUST_SECRET`**：阶段 3.2 生成的那串
3. **下面这段配置要求**

### 8.2 给 SSO 团队的配置要求（可直接转发）

> 请在已完成认证的转发位置上，加入以下配置。
>
> **必须注入的请求头**
>
> | 头 | 内容 |
> |---|---|
> | `X-Agent-User` | 用户工号。小写字母数字与 `-`，最长 54 字符 |
> | `X-Agent-Roles` | 用户所属角色/组，逗号分隔（可选） |
> | `X-Agent-Trust` | 我方提供的共享密钥，原样透传 |
>
> **必须的代理设置**（nginx 示例；其它产品请找等价项）
>
> ```nginx
> location /gaussdb-agent/ {
>     proxy_set_header X-Agent-User   $remote_user;
>     proxy_set_header X-Agent-Roles  $user_groups;
>     proxy_set_header X-Agent-Trust  "<共享密钥>";
>     proxy_pass http://gateway.gaussdb-agent.svc/;
>
>     proxy_buffering    off;    # ← 必需
>     proxy_cache        off;    # ← 必需
>     proxy_http_version 1.1;    # ← 必需
>     proxy_read_timeout 1h;     # ← 必需
>     gzip               off;
> }
> ```
>
> **为什么这四行是必需的**：本系统用 SSE（`text/event-stream`）向浏览器推送模型输出，
> 每 10 秒一次心跳。任何一层缓冲响应体，页面就会一直转圈、消息迟迟不出来 ——
> 表现不像「断开」，像「卡住」，最难排查。
>
> **请一并确认两条硬限制**
>
> 1. 是否存在「单个连接最长 N 分钟」的限制？SSE 是永不结束的连接。
> 2. 闲置回收（若有）是按**字节活动**还是按**新请求数**判定？
>    本系统开着页面发呆时有心跳但没有新请求，按请求数判会误杀。

### 8.3 SSO 未就绪时如何继续

不必等。用 `curl` 模拟 SSO 的效果，先把阶段 9 做完：

```bash
curl -H "X-Agent-Trust: $TRUST" -H "X-Agent-User: u0001" http://127.0.0.1:18080/...
```

## 阶段 9：开通第一个用户并端到端验收

### 9.1 开通一个用户

开通 = **创建他本人的 GRMP 令牌 Secret**。其余（Pod、口令、NAS 目录）网关自动完成。

```bash
kubectl -n gaussdb-agent create secret generic grmp-token-u0001 \
  --from-literal=GRMP_AUTH_TOKEN='<该用户的中间件令牌>'
```

知识库管理员另需在角色里带上 `kb-admin`（由 `X-Agent-Roles` 头传入），
或写进 ConfigMap `agent-roles`。

> **为什么网关不自动建这个 Secret**：令牌由贵方中间件按人签发，网关无从得知。
> 缺它时用户会看到 503「您的环境尚未开通」，网关日志里写明缺的是哪个 Secret。

### 9.2 验收清单

逐条执行，**全绿才算上线**：

```bash
TRUST=<共享密钥>; GW=http://127.0.0.1:18080
H=(-H "X-Agent-Trust: $TRUST" -H "X-Agent-User: u0001")
```

| # | 验什么 | 命令 | 期望 |
|---|---|---|---|
| 1 | 首次访问自动建 Pod | `time curl -s -o /dev/null -w "%{http_code}\n" "${H[@]}" $GW/global/health` | `200`，30 秒内 |
| 2 | Pod 真的建了 | `kubectl -n gaussdb-agent get deploy runtime-u0001` | `READY 1/1` |
| 3 | 能对话 | 见下方 9.3 | 模型正常回复 |
| 4 | 能连数据库 | 对话里说「登录 `<实例IP>` 的 `<库名>`」 | 返回已登录与主备状态 |
| 5 | 诊断技能可用 | 对话里说「看下当前有没有慢 SQL」 | 返回报告 |
| 6 | 知识库可查 | 对话里说「知识库里有没有 CPU 相关的案例」 | 返回案例或「无」 |
| 7 | **导入被正确拒绝**（普通用户） | 对话里说「帮我导入一份工单」 | 答「本环境不含导入功能」 |
| 8 | 未开通用户被挡 | 换 `X-Agent-User: u9999` 重复第 1 条 | `503`，日志写明缺哪个 Secret |
| 9 | 无信任凭据被挡 | 去掉 `X-Agent-Trust` 重复第 1 条 | `403` |
| 10 | 跨用户不可见 | 在 u0001 的 Pod 里 `ls /nas` | 只有 `me` 和 `kb` |
| 11 | 回收生效 | 见 9.4 | 副本数归 0 |
| 12 | 重连恢复 | 回收后重复第 1 条 | `200`，会话还在 |

### 9.3 第 3 条的具体做法

```bash
S=$(curl -s "${H[@]}" -X POST "$GW/session?directory=/data/state/workspace" \
      -H 'content-type: application/json' -d '{}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])')

curl -s "${H[@]}" -X POST "$GW/session/$S/message?directory=/data/state/workspace" \
  -H 'content-type: application/json' -d '{"parts":[{"type":"text","text":"只回四个字:部署验收"}]}'
```

也可以直接用浏览器：`$GW/L25hcy9tZS93b3Jrc3BhY2U`
（那串是 `/nas/me/workspace` 的 base64url，是 opencode 的项目路由）。

> **不要落在 `/`**：那一页的项目列表是浏览器本地记的，新浏览器为空，用户会以为系统坏了。

### 9.4 第 11 条的具体做法

```bash
# 把活动时间改成很久以前,等回收器扫描(默认 120 秒一轮)
kubectl -n gaussdb-agent annotate deploy runtime-u0001 \
  "gaussdb-agent/last-activity=$(( $(date +%s) - 9999 ))" --overwrite

sleep 150
kubectl -n gaussdb-agent get deploy runtime-u0001 -o jsonpath='{.spec.replicas}'
# 期望:0
```

### 10.5 升级流程

```bash
# 1) 推新镜像
docker push $REG/gaussdb-agent-runtime:agent-v1.1.0-oc1.18.27     # 三个都推

# 2) 改升级开关
kubectl -n gaussdb-agent patch configmap gateway-config --type merge \
  -p '{"data":{"USER_IMAGE_TAG":"agent-v1.1.0-oc1.18.27"}}'

# 3) 网关自身也升(独立于用户镜像)
kubectl -n gaussdb-agent set image deploy/gateway \
  gateway=$REG/gaussdb-agent-gateway:agent-v1.1.0-oc1.18.27
kubectl -n gaussdb-agent rollout status deploy/gateway
```

**这样升级不影响正在使用的人**：他们的 Pod 不动，下次登录（或被回收后重连）才换新版。

要强制全体升级：`kubectl -n gaussdb-agent delete deploy -l app=gaussdb-agent`
（NAS 数据保留，用户重新登录即恢复）。**请在业务低谷期做**，正在进行的对话会中断。

### 10.6 回滚

把 `USER_IMAGE_TAG` 改回旧标签 + 网关镜像改回旧版即可。
**NAS 上的数据格式在小版本间兼容**，回滚不需要恢复数据。

## 附录 A：常见问题定位

| 现象 | 先看 | 常见原因 |
|---|---|---|
| 网关 CrashLoop | `logs -l app=agent-gateway` | 配置不全（刻意拒绝启动），按报错改 |
| 网关 `连不上 k8s API` | `gateway-policy` 的出站 | apiserver 地址段没按实际填（§7） |
| 用户 503 | 网关日志 | 缺 `grmp-token-<工号>` |
| 用户 504 | `describe deploy runtime-<工号>` | 镜像拉不到 / 资源不足 / NAS 挂不上 |
| 用户 403 | SSO 侧 | `X-Agent-Trust` 没注入或值不对 |
| 页面一直转圈 | SSO 侧代理 | 没关缓冲（§8.2） |
| 页面「已中断」 | 用户操作 | 空输入框按回车 = 中断。刷新重发即可 |
| Pod 起不来，日志停在 `独占标记` | NAS | `.owner` 被上一个 Pod 占着；等 90 秒过期或人工删 |
| 对话历史丢了一段 | Pod 日志搜「非优雅」 | 上次是 OOMKill/驱逐，NAS 上有 `.unclean-*` 快照 |
| 知识库查不到应该有的案例 | `kb.py health` | 纯文件模式无语义召回，需配 embedding |

## 附录 C：镜像拉取令牌的管理

采用「从镜像仓库拉取」路线时，我方会提供一个**只读令牌**（`read:packages`）。
它是一个需要有人负责的凭据，请纳入贵方的密钥管理流程。

| 项 | 说明 |
|---|---|
| 能做什么 | 拉取本项目的三个容器镜像；访问本项目的源码仓库 |
| 用途 | 只在**首次部署**与**升级取新镜像**时使用；拉完推进内网仓库后，集群不再需要它 |
| 存放 | **不要**写进 K8s 清单、部署脚本或 CI 配置。建议放贵方密钥管理系统，取用时临时注入 |
| 轮换 | 人员变动、到期、或怀疑泄露时请联系我方重签。轮换不影响已拉到内网仓库的镜像 |
| 失效影响 | 只影响「再次从外网取新版本」，**不影响已部署环境的运行** |
| 泄露处置 | 立即联系我方作废并重签。已部署环境不受影响，但请同步排查是否有非预期的仓库访问 |

**集群本身不需要这个令牌。** 正确做法是：跳板机用它拉取 → 推进贵方内网仓库 →
清单里的 `image:` 指向内网仓库。集群只认内网仓库，与外网彻底解耦。

若清单里直接写 `ghcr.io/...` 地址，集群每次拉镜像都要出外网并持有令牌，
这既不符合多数行内网络策略，也会让令牌轮换变成一次全集群改动 —— **不建议**。
